    Actions

    Action components are where the user triggers something: click, pick from a list, confirm. They carry intent — a click changes data, navigates, or starts a flow. That's why this category groups both the direct trigger (Button) and the elements around an action: contextual hint (Tooltip), a set of secondary actions (DropdownMenu), an anchored panel (Popover), and the safeguard before something destructive (ConfirmDialog).

    Reach for this page when you need the user to do something. For data entry (text, selection, dates) see inputs; to present collections, see data.

    Button

    Section buttons of the gallery — run it locally to interact.

    When to use: the primary or secondary action of any screen — submit a form, open a modal, navigate. The default action trigger.

    Primary button with variants, sizes, and a loading state.

    import { Button } from "tempest-react-sdk";
import { Plus, Trash } from "lucide-react";

<Button>Save</Button>;
<Button variant="danger" leftIcon={<Trash size={16} />}>
  Delete
</Button>;
<Button variant="outline" loading>
  Loading…
</Button>;
<Button variant="link" rightIcon={<ArrowRight size={14} />}>
  See more
</Button>;
<Button iconOnly aria-label="Add">
  <Plus size={16} />
</Button>;
<Button fullWidth pill>
  CTA
</Button>;
    Prop Type Default
    variant "primary" \| "secondary" \| "success" \| "danger" \| "soft" \| "outline" \| "ghost" \| "link" "primary"
    size "xs" \| "sm" \| "md" \| "lg" \| "xl" "md"
    loading boolean false
    fullWidth boolean false
    iconOnly boolean (square, requires aria-label) false
    pill boolean (pill border-radius) false
    leftIcon ReactNode —
    rightIcon ReactNode —
    href string — renders <a> instead of <button> —

    iconOnly needs an accessible label

    iconOnly removes the visible text, so screen readers have nothing to announce. Always pass aria-label describing the action (aria-label="Delete"). Without it the button is a mute icon to assistive tech.

    loading blocks double-clicks

    loading disables the button and sets aria-busy="true" — it's the standard for async submits. Turn it on the moment you fire the request to avoid duplicate requests from repeated clicks.

    The label stays the accessible name while loading: it is removed from paint only (the spinner replaces it on screen, at the same width), so a screen reader announces "Save, button, unavailable" — not a nameless "button". The spinner is decorative (aria-hidden) and adds nothing to the name; the state comes from aria-busy and disabled. This holds for <button>, href and ButtonSlot.

    A button that navigates: href

    A call to action that takes the user somewhere — "Contact us" on WhatsApp, mailto:, "See plans", "Download" — is a link, not a button. With onClick={() => location.assign(url)} it loses the middle click, Ctrl+click, "open in new tab", the URL preview and the crawler; with <a><Button /></a> it is invalid HTML with two tab stops. With href, Button renders an <a> with the same look across every variant and size:

    import { Button } from "tempest-react-sdk";
import { MessageCircle } from "lucide-react";

export function Ctas() {
  return (
    <>
      <Button href="/plans" variant="outline">
        See plans
      </Button>
      <Button
        href="https://wa.me/5586999999999"
        target="_blank"
        leftIcon={<MessageCircle size={16} />}
      >
        Contact us
      </Button>
    </>
  );
}
    • target and rel are forwarded.
    • The ref is typed per mode: HTMLButtonElement without href, HTMLAnchorElement with it. type exists only in the <button> mode — <Button href="/x" type="submit"> does not compile.

    target=_blank gets noopener noreferrer on its own

    Without noopener, the opened tab receives window.opener and can redirect yours. It is a mechanical rule with one right answer, so it lives in the component: the tokens you pass in rel stay, and the missing ones are added without duplicates.

    Disabled link

    <a> has no disabled. With disabled or loading, the link gets aria-disabled="true", role="link" and tabIndex={-1}, loses its href, and has its click and middle click cancelled — it does not navigate and is announced as unavailable.

    The URL scheme is checked

    The href goes through the same list as safeLinkUrl: http:, https:, mailto:, tel:, sms: and relative URLs. Any other scheme — javascript:, data:, and the variants with upper case or a tab in the middle — becomes the same inert, aria-disabled link as the disabled case. React 19 blocks javascript: on its own, but React 18, inside the peer range, writes the href as given, and a CTA built from API data would become a clickable script. A link to a custom scheme (whatsapp:, an app deep link) goes through ButtonSlot with your own <a>.

    Why InstallButton does not take href

    Its click opens the install prompt or reveals the instruction — an action, not a navigation. It inherits the props of the <button> mode.

    ButtonSlot

    When to use: give the Button look to another element — typically react-router's Link, to change routes without reloading the page.

    ButtonSlot renders no element of its own: it applies the button's classes, props and ref to its single child (the asChild/Slot pattern). It takes the same look props as Button (variant, size, loading, disabled, fullWidth, iconOnly, pill, leftIcon, rightIcon), and Button never imports the router.

    import { ButtonSlot } from "tempest-react-sdk";
import { Link, NavLink } from "react-router";

export function Menu() {
  return (
    <>
      <ButtonSlot variant="soft">
        <Link to="/account">My account</Link>
      </ButtonSlot>
      <ButtonSlot variant="ghost">
        <NavLink to="/" className={({ isActive }) => (isActive ? "active" : "")}>
          Home
        </NavLink>
      </ButtonSlot>
    </>
  );
}

    How the props combine:

    • Classes are added. A function className (NavLink's) stays a function.
    • ButtonSlot's props win over the child's, because they carry the disabled semantics.
    • Both handlers run: ButtonSlot's first; if it calls preventDefault(), the child's does not run.
    • Both refs — the child's and ButtonSlot's — receive the same node.
    • A child with target="_blank" also gets noopener noreferrer.

    Disabled around a Link

    With disabled or loading, the child gets aria-disabled="true" and tabIndex={-1}, and the click and middle click are cancelled — the Link skips its navigation because the event arrives prevented. A plain <a href> also loses its href; a Link's href is computed by the Link and stays in the DOM.

    Why a component and not an asChild prop

    The prop merge and ref composition cost ~0.6 kB brotli. An asChild prop is a runtime branch no bundler can remove, so every app using Button would pay for it. As a separate export, ButtonSlot drops out of the bundle of anyone who does not import it: the { Button } slice measures 1.21 kB with href, against 1.71 kB with asChild inside Button.

    FloatingActionButton

    Section material of the gallery — run it locally to interact.

    When to use: the primary, persistent action of a screen (create, compose, add) that should always be reachable, floating over the content. Round when icon-only, or extended (pill) when given a label.

    By default it is fixed to the bottom-right corner; pass position="none" to place it inline (e.g. inside a NavigationRail). Spreads all native <button> props (onClick, disabled, etc.).

    import { FloatingActionButton } from "tempest-react-sdk";
import { Plus } from "lucide-react";

<FloatingActionButton icon={<Plus />} aria-label="New" position="none" onClick={create} />;
<FloatingActionButton icon={<Plus />} label="New order" onClick={create} />;
    Prop Type Default
    icon ReactNode —
    label ReactNode (present → extended FAB) —
    position "bottom-right" \| "bottom-left" \| "none" "bottom-right"
    size "sm" \| "md" \| "lg" "md"
    variant "primary" \| "surface" "primary"
    ... All HTMLButtonElement attributes —

    An icon-only FAB needs aria-label

    Without a visible label, the round FAB has no accessible name. Always pass aria-label describing the action (aria-label="New"); when a label is present, it already serves as the name.

    Tooltip

    Section navigation of the gallery — run it locally to interact.

    When to use: give extra context to a control whose meaning isn't obvious — typically iconOnly buttons. Never for critical information.

    A hover tooltip in a portal: it escapes an overflow ancestor (a DataTable cell, say) and flips to the opposite side at the screen edge. Shows on hover and on keyboard focus.

    import { Button, Tooltip } from "tempest-react-sdk";
import { Trash } from "lucide-react";

export function ExcluirComDica() {
    return (
        <Tooltip content="Delete permanently" placement="bottom" openDelay={300}>
            <Button variant="danger" iconOnly aria-label="Delete">
                <Trash size={16} />
            </Button>
        </Tooltip>
    );
}
    Prop Type Default
    content ReactNode —
    placement "top" \| "right" \| "bottom" \| "left" "top"
    openDelay number (ms before showing) 150
    disabled boolean (turn off, trigger unchanged) false
    portal boolean (renders in document.body) true

    Escape hides the tooltip without moving the pointer or the focus, as WCAG 2.2 SC 1.4.13 asks. Inside a Modal, the first Escape hides the tooltip and the second one closes the modal.

    Don't hide essential information in a tooltip

    Touch users have no hover — they'll never see the content. A tooltip is reinforcement, not the only source of information needed to complete the task.

    DropdownMenu

    Section overlays of the gallery — run it locally to interact.

    When to use: group secondary actions behind a single trigger ("More actions", a profile menu) when they don't fit the main bar.

    A dropdown menu of actions. Keyboard nav (↑↓ Home End Esc). Each entry needs a stable id (used as the React key).

    import { Button, DropdownMenu } from "tempest-react-sdk";

export function MaisAcoes({
    navigate,
    logout,
}: {
    navigate: (to: string) => void;
    logout: () => void;
}) {
    return (
        <DropdownMenu
            trigger={<Button variant="ghost">More actions</Button>}
            items={[
                { type: "label", id: "h", label: "Account" },
                {
                    type: "item",
                    id: "edit",
                    label: "Edit profile",
                    onSelect: () => navigate("/profile"),
                },
                { type: "separator", id: "s1" },
                { type: "item", id: "logout", label: "Sign out", onSelect: logout, danger: true },
            ]}
        />
    );
}
    Entry type Fields
    "item" id, label, icon?, onSelect, disabled?, danger?
    "checkbox" id, label, icon?, checked, onSelect, disabled?
    "label" id, label
    "separator" id

    Component props: trigger (ReactElement), items (DropdownMenuEntry[]), placement ("bottom-start" \| "bottom-end" \| "top-start" \| "top-end", default "bottom-start"), portal (boolean, default true — see In a table row).

    In a table row

    The per-row action menu is the most common case of an admin panel, and it is exactly where an in-flow menu breaks: the DataTable wrapper scrolls horizontally (overflow-x: auto), and by the CSS rules that forces overflow-y to auto too. That is why the menu renders in a portal by default, anchored to its trigger.

    import { Button, DataTable, DropdownMenu } from "tempest-react-sdk";

interface User {
    id: string;
    name: string;
}

export function UsersTable({
    users,
    open,
    remove,
}: {
    users: User[];
    open: (id: string) => void;
    remove: (id: string) => void;
}) {
    return (
        <DataTable<User>
            data={users}
            rowKey={(user) => user.id}
            columns={[
                { key: "name", header: "Name" },
                {
                    key: "id",
                    header: "",
                    render: (user) => (
                        <DropdownMenu
                            placement="bottom-end"
                            trigger={
                                <Button variant="ghost" iconOnly aria-label="Actions">
                                    ⋮
                                </Button>
                            }
                            items={[
                                {
                                    type: "item",
                                    id: "view",
                                    label: "View profile",
                                    onSelect: () => open(user.id),
                                },
                                {
                                    type: "item",
                                    id: "delete",
                                    label: "Delete",
                                    danger: true,
                                    onSelect: () => remove(user.id),
                                },
                            ]}
                        />
                    ),
                },
            ]}
        />
    );
}

    What the portal fixes, measured in Chrome at 1440 px with the three-entry menu on the last row:

    In flow (before 0.67.0) In a portal
    Visible entries 1 of 3 3 of 3
    No room below opened below the fold flips above the trigger
    Table scrolls with the menu open — the menu follows the trigger
    Inside a Modal — paints on top of the modal

    Why the portalled menu sits above Modal

    In a portal the menu lives in document.body, next to the modal — it no longer inherits the modal's stacking. It uses --tempest-z-popover (1150), above --tempest-z-modal (1100). With --tempest-z-dropdown (1000), measured, a menu opened inside a modal sat behind it.

    portal={false} brings back the in-flow menu

    Use it when the container must own the menu's clipping or stacking on purpose. The same portal exists on Popover and Tooltip.

    An entry that toggles

    type: "checkbox" renders role="menuitemcheckbox" with aria-checked — which is how a screen reader announces "checked" instead of leaving the state invisible.

    import { useState } from "react";
import { Button, DropdownMenu } from "tempest-react-sdk";

export function CallMenu({ toggleTheme }: { toggleTheme: () => void }) {
    const [quiet, setQuiet] = useState(false);

    return (
        <DropdownMenu
            trigger={<Button variant="ghost">More options</Button>}
            items={[
                {
                    type: "checkbox",
                    id: "quiet",
                    label: "Mute call sounds",
                    checked: quiet,
                    onSelect: () => setQuiet((value) => !value),
                },
                { type: "separator", id: "s" },
                { type: "item", id: "theme", label: "Toggle theme", onSelect: toggleTheme },
            ]}
        />
    );
}

    A plain item closes, a checkbox does not

    Selecting an "item" fires onSelect and closes the menu. A "checkbox" toggles and leaves the menu open, because adjusting two preferences in a row is the ordinary case and closing after the first would make the second a second trip.

    Keyboard

    role="menu" is a promise about the keyboard, and the component keeps it — the pattern is the APG Menu Button:

    Key On the trigger In the open menu
    Enter / Space opens, focuses the first entry activates the focused entry
    ↓ opens, focuses the first entry next, wrapping
    ↑ opens, focuses the last entry previous, wrapping
    Home / End — first / last
    Esc — closes and returns focus to the trigger
    Tab follows the page closes and follows the page from the trigger

    Managed focus — Tab does not walk the menu

    Entries carry tabIndex={-1} and only the active one is 0. Without that, Tab would step through entry by entry and do the job the arrow key should — which is worse than inaccessible, because the widget looks like it works while contradicting what role="menu" announced. Disabled entries, label and separator are never a stop.

    Popover

    When to use: a floating panel with arbitrary content (filters, a mini-form, a preview) anchored to a trigger — when you need more than a list of actions.

    A generic floating panel (anchor + outside-click + Esc dismiss). Works controlled (open + onOpenChange) or uncontrolled (defaultOpen).

    import { useState } from "react";
import { Button, Checkbox, Popover, Stack } from "tempest-react-sdk";

export function Filtros() {
    const [open, setOpen] = useState(false);

    return (
        <Popover
            open={open}
            onOpenChange={setOpen}
            placement="bottom"
            trigger={<Button>Filters</Button>}
        >
            <Stack gap={3}>
                <Checkbox label="Active only" />
                <Checkbox label="Paid" />
                <Button onClick={() => setOpen(false)}>Apply</Button>
            </Stack>
        </Popover>
    );
}
    Prop Type Default
    trigger ReactElement (cloned with handlers) —
    open boolean — (controlled)
    onOpenChange (open: boolean) => void —
    defaultOpen boolean (uncontrolled usage) false
    placement "top" \| "bottom" \| "left" \| "right" "bottom"
    closeOnEsc boolean true
    closeOnOutsideClick boolean true
    portal boolean (renders in document.body) true

    Flips at the screen edge

    In a portal (the default), the panel moves to the opposite side when the requested placement does not fit the viewport, and is kept inside it with an 8 px margin. Scrolling the page or a container with the panel open carries it along with the trigger.

    Tab enters the panel, even in a portal

    In a portal the panel lives at the end of body, and the browser would reach it last. Popover restores the in-flow order: Tab from the open trigger enters the panel's first field, Tab on its last field moves on to what follows the trigger, and Shift+Tab walks back the same way.

    ConfirmDialog

    Section modal of the gallery — run it locally to interact.

    When to use: the last barrier before an irreversible or costly action (delete, overwrite, cancel). Always with variant="danger" when destructive.

    A pre-built destructive prompt on top of Modal (text + 2 buttons).

    import { useState } from "react";
import { ConfirmDialog } from "tempest-react-sdk";

export function ExcluirUsuario({
    user,
    deleteUser,
}: {
    user: { id: string; name: string };
    deleteUser: (id: string) => Promise<void>;
}) {
    const [open, setOpen] = useState(false);
    const [deleting, setDeleting] = useState(false);

    return (
        <ConfirmDialog
            open={open}
            title="Delete user"
            description={`This cannot be undone. Delete ${user.name}?`}
            confirmLabel="Yes, delete"
            cancelLabel="Cancel"
            variant="danger"
            loading={deleting}
            onConfirm={async () => {
                setDeleting(true);
                await deleteUser(user.id);
                setDeleting(false);
                setOpen(false);
            }}
            onCancel={() => setOpen(false)}
        />
    );
}
    Prop Type Default
    open boolean —
    title ReactNode —
    description ReactNode —
    confirmLabel string "Confirmar"
    cancelLabel string "Cancelar"
    variant "primary" \| "danger" "primary"
    confirmIcon ReactNode (becomes the confirm button's leftIcon) —
    loading boolean (spinner on confirm + locks the dialog, see below) false
    onConfirm () => void \| Promise<void> —
    onCancel () => void —

    Control loading during the request

    onConfirm accepts a promise, but ConfirmDialog doesn't manage the loading state itself — pass loading={deleting} driven by your own state while the async action runs.

    While loading, the dialog does not close

    While loading is true, every way out is closed, not just the Cancel button: Esc and a backdrop click don't call onCancel, and the close button (×) is hidden. Cancelling mid-request would leave the screen saying "cancelled" with the operation still in flight — on a sign-out that revokes the session server-side, the user would be signed out anyway. The lock is derived from loading; there is no other prop to keep in sync. useModals().confirm() inherits the same behaviour.

    With confirmIcon, the confirm button gets an icon before its label — the accessible name is still confirmLabel:

    import { useState } from "react";
import { LogOut } from "lucide-react";
import { ConfirmDialog } from "tempest-react-sdk";

export function SignOut({ signOut }: { signOut: () => Promise<void> }) {
    const [open, setOpen] = useState(false);
    const [leaving, setLeaving] = useState(false);

    return (
        <ConfirmDialog
            open={open}
            title="Sign out"
            description="You will need to sign in again on this device."
            confirmLabel="Sign out"
            cancelLabel="Cancel"
            confirmIcon={<LogOut size={16} />}
            variant="danger"
            loading={leaving}
            onConfirm={async () => {
                setLeaving(true);
                try {
                    await signOut();
                    setOpen(false);
                } finally {
                    setLeaving(false);
                }
            }}
            onCancel={() => setOpen(false)}
        />
    );
}

    Default labels are Portuguese

    confirmLabel/cancelLabel default to "Confirmar"/"Cancelar". Pass explicit English strings in EN-locale apps.

    InstallButton

    Section pwa of the gallery — run it locally to interact.

    PWA install button wired to useInstallPrompt. Where the browser fires beforeinstallprompt, the click installs. Where it does not — iOS Safari, an app's embedded browser (Instagram, WhatsApp, Facebook…), and the Android Chromium forks (Mi Browser, UC, Opera Mini, Huawei) — the click reveals that platform's instruction instead of the button disappearing. Inherits every Button prop.

    import { InstallButton } from "tempest-react-sdk";
import { Download } from "lucide-react";

<InstallButton variant="primary" leftIcon={<Download size={18} />} />;
    Prop Type Default
    label ReactNode "Instalar app"
    hintLabel ReactNode "Como instalar"
    onResult (o: "accepted" \| "dismissed" \| "unsupported") => void —
    renderHint (input: InstallHintInput) => ReactNode defaultInstallHint
    manualFallbackDelayMs number 3000
    wrapperClassName string —
    … all Button props (variant, size, leftIcon) —

    Until v0.65.0 both disappeared exactly where the user needs them

    InstallButton and InstallBanner were built on useBeforeInstallPrompt, so they rendered null in every browser that never fires the event. iOS Safari is precisely that case — and it is where the install path hides behind the Share sheet, which nobody finds unless told. In practice every app kept a local copy of these two components just to add the ios and manual paths.

    null now means only that there is nothing to offer: already installed, running standalone, or inside the decline window.

    renderHint swaps the copy without rewriting the component

    The default is PT-BR and names the real menu entries — on Android it also offers the intent:// link that reopens the page in Chrome, which is the only path that reaches a real install on a fork with no install entry at all.

    import { InstallButton, defaultInstallHint } from "tempest-react-sdk";

<InstallButton
    renderHint={(input) =>
        input.method === "ios" ? <MyIOSSteps /> : defaultInstallHint(input)
    }
/>;

    InstallHintInput carries method ("native" | "ios" | "open-in-browser" | "manual" | "none") and openInChromeIntent.

    Inside an app's embedded browser

    A link shared on WhatsApp or Instagram opens inside the app, in an embedded browser. Nothing installs there: on the iPhone only Safari has Add to Home Screen, and on Android the web view never fires beforeinstallprompt. useInstallPrompt recognises that case and resolves method: "open-in-browser" — and InstallButton and InstallBanner show the right way out with no change in the app:

    Where What the default instruction shows
    iPhone (Instagram, WhatsApp, Facebook, TikTok…) "Toque em ⋯ e escolha Abrir no Safari (ou Abrir no navegador)" + a Copiar link button
    Android (the same apps) an Abra no Chrome link (intent://) + a Copiar link button

    The Copiar link button is InstallCopyLink. It tries navigator.clipboard.writeText, then execCommand("copy") — embedded browsers often deny the Clipboard API — and, when neither works, shows the address in a read-only field already selected, so the user copies it with a long press. It is the path that works in every app, whatever its menu calls "open in browser".

    To translate it, use it inside your own renderHint:

    import { InstallButton, InstallCopyLink, defaultInstallHint } from "tempest-react-sdk";

export function InstallCta() {
    return (
        <InstallButton
            hintLabel="How to install"
            renderHint={(input) =>
                input.method === "open-in-browser" ? (
                    <>
                        Tap <strong>⋯</strong> and choose <strong>Open in Safari</strong>.
                        <InstallCopyLink
                            labels={{
                                copy: "Copy link",
                                copied: "Link copied",
                                manual: "Long-press the link to copy it.",
                                field: "Page link",
                            }}
                        />
                    </>
                ) : (
                    defaultInstallHint(input)
                )
            }
        />
    );
}
    Prop Type Default
    url string window.location.href at click time
    labels Partial<InstallCopyLinkLabels> copy: "Copiar link", copied: "Link copiado", manual: "Toque e segure o link para copiar.", field: "Link da página"

    An older renderHint keeps working

    A renderHint written only for "ios" and "manual" returns null for "open-in-browser". The component treats null (or undefined) as "use the default" and falls back to defaultInstallHint — without that, the Como instalar button would reveal nothing inside Instagram.

    InstallBanner

    Dismissible bottom banner inviting the user to install the PWA, on the same useInstallPrompt. Where the browser cannot be prompted, the button becomes "Como instalar" and reveals the platform's instruction inside the banner. storageKey remembers the dismissal across reloads.

export function Instalar() {
    return (

            title="Install the app"
            description="Offline access and a home-screen shortcut."
            storageKey="meu-app:install-dismissed"
        />
    );
}

    onResult (o) => void —

    Per route, above the bottom nav, and with a guide

    Three decisions every app used to make around its own copy of the banner, now props:

    import { Link, useLocation } from "react-router";
import { InstallBanner } from "tempest-react-sdk";

const NO_BANNER = ["/camera", "/login", "/install"];

export function InstallPromptBanner() {
    const { pathname } = useLocation();

    return (
        <InstallBanner
            title="Install the app"
            description="Offline access and a home-screen shortcut."
            storageKey="meu-app:install-dismissed"
            visible={!NO_BANNER.some((route) => pathname.startsWith(route))}
            position="bottom"
            guide={<Link to="/install">See the full guide</Link>}
        />
    );
}
    • visible hides without unmounting. It looks the same as {show && <InstallBanner />}, but it is not: without storageKey the dismissal lives in component state, and unmounting forgot it — the dismissed banner came back on the next route that showed it. The SDK does not read the route itself on purpose: that way it needs no router context to render, and the rule of which routes hide it stays with the app.
    • position="bottom" pins the banner to the bottom of the viewport (fixed, centered, up to 32rem), above the safe area and above --tempest-bottom-nav-height. Inside an AppShell with bottomNav, the shell measures and publishes that variable itself — the banner sits above the bar with no configuration. With a bar of your own, publish its height in the same variable. The "inline" default keeps the usual behavior: the banner stays where you render it.
    • guide shows right after the platform instruction ("ios" and "manual"), when the user opens "Como instalar". It is a node, not an href, so you pass your router's Link and the guide page opens without reloading the app.

    Accepting closes the banner — and it stays closed

    Up to v0.86.0 the banner disappeared on accept and came back 3 s later offering "Como instalar": the stored event was dropped, the tab that installed is still in display-mode: browser, and the manual fallback took over. Measured with the component itself in jsdom: visible false right after accepted, true with the "Como instalar" button at 3.5 s, even after appinstalled. Now useInstallPrompt remembers the session's install (accepted or appinstalled) and resolves method: "none" until the browser fires a fresh beforeinstallprompt — which only happens if the app is uninstalled. The same holds for InstallButton.

    declineCooldownMs changes what is stored — and respects what was already there

    Without it, a dismissal written to storageKey is permanent, which is what the component always did (it stores "1"). With it, a timestamp is stored and the banner returns after the window.

    A key already holding "1" still counts as a permanent dismissal even with declineCooldownMs configured: it was written under the old contract, and reviving a banner the user switched off is worse than leaving it off.

    PostInstallPrompt

    Overlay shown in the browser tab after the app is installed from it. Without it, the user accepts the install, the tab looks unchanged, and they keep using the site without knowing the app is already on the home screen.

    import { PostInstallPrompt } from "tempest-react-sdk";

export function Root() {
    return (
        <PostInstallPrompt
            title="FAMACHApp installed"
            onContinue={() => console.info("kept using the browser")}
        />
    );
}

    Mount it once, at the app root. It opens by itself when useBeforeInstallPrompt's installed turns true — the user accepted the prompt or the browser fired appinstalled — and offers two ways out: "Fechar esta aba" (close this tab) and "Continuar no navegador" (keep using the browser; Escape and a backdrop click count as continuing).

    closeLabel string "Fechar esta aba"
    continueLabel string "Continuar no navegador"
    closeBlockedMessage ReactNode PT-BR copy asking the user to close the tab
    onContinue () => void —
    className string —

    There is no \"open the installed app\" on the web — and the component does not pretend there is

    No web API opens an installed PWA from a browser tab; a link to the start_url opens in the same tab on most browsers. That is why there is no "Open now" button: what the tab can do is close itself, and only when the browser allows it.

    Measured in headless Chromium 153 (15/11/2026): a tab the user opened directly at the URL closes with window.close() while history.length is 1; a single pushState and the call is ignored ("Scripts may close only the windows that were opened by them."). A tab opened by window.open closes even after navigating. An SPA that changed route once is already past that point — so the component predicts the rule and, when it will not allow it, does not show the button: it shows closeBlockedMessage, asking the user to close the tab and open the app from its icon. If the browser ignores close() anyway, the button gives way to the same message.

    It only opens where there is an install signal

    appinstalled is fired by Chromium browsers (Chrome, Edge, Samsung Internet), whatever the install path was — prompt, address-bar icon or menu. Safari (iOS and macOS) and Firefox do not fire it, so there the overlay never opens: there is no signal to rely on.

    ShareActions

    Section meta of the gallery — run it locally to interact.

    When to use: the user is about to spread something from the app — a ride, a product, an event — on WhatsApp or another network. Three ready buttons: WhatsApp, the system share sheet and "Copy link".

    import { ShareActions } from "tempest-react-sdk";

export function ShareRide({ id }: { id: string }) {
  const url = `https://app.example.com/c/${id}`;
  return (
    <ShareActions
      title="Ride Picos → Teresina"
      text="Friday, 07:05 · R$ 25.00 per seat · 3 seats"
      url={url}
      imageUrl={`${url}/og.png`}
    />
  );
}
    Prop Type Default
    url string — the link being shared —
    title string —
    text string — url is appended on WhatsApp —
    imageUrl string — sent as a file where the device accepts one —
    imageFileName string path name, or preview.<ext>
    actions ("whatsapp" \| "native" \| "copy")[] ["whatsapp", "native", "copy"]

    variant ButtonVariant "outline"
    size ButtonSize "md"
    onShare (outcome: ShareOutcome) => void —

    What each button does:

    • WhatsApp is a real link to https://wa.me/?text=… (built by whatsAppShareUrl), carrying the text and the link. Being an <a>, it needs no popup permission and opens the app on a phone. The preview image comes from the Open Graph tags of the linked page — see the recipe.
    • Share opens the system sheet through useShare, with the image attached where the device accepts files. It renders only where navigator.share exists.
    • Copy link tries the Clipboard API, then execCommand("copy"); when both are refused (some in-app browsers) it shows the link in a read-only field, already selected, with a hint to press and hold. Success is announced through a role="status" region.

    The choice is by capability, not user agent

    The "Share" button renders where navigator.share exists — not where the user agent says "mobile". Desktop Chrome on Windows and macOS has the system sheet and gets the button; desktop Firefox and Chrome on Linux do not. Sniffing "phone" gets both sides wrong.

    Translatable texts

    The defaults go through I18nProvider (tempest.share.whatsapp, .native, .copy, .copied, .manual, .field): an English app gets "Share on WhatsApp" with no setup. labels wins over both.

    Recap

    Component Use for Trigger
    Button Fire the primary/secondary action click
    FloatingActionButton Floating, persistent primary action click
    InstallButton Install the PWA, or teach how where no prompt exists click
    InstallBanner Dismissible invite to install the PWA click
    PostInstallPrompt Tell the tab the app is already installed appinstalled
    ShareActions Spread a link: WhatsApp, system sheet, copy click
    ShareButton One share button, through the path the browser has click
    Tooltip Non-critical context on a control hover/focus
    DropdownMenu A list of secondary actions (closes on pick) click
    Popover A floating panel with arbitrary content click
    ConfirmDialog Confirm a destructive action before running it —

    Key accessibility points:

    • Destructive actions should use variant="danger".
    • Button.loading is the standard for async submits — it blocks double-clicks.
    • Tooltips should not contain critical information (touch users don't see hover).
    • iconOnly requires aria-label.
