    Forms

    Forms almost always stall on two problems that have nothing to do with each other: how the fields lay out on screen and how the values are validated. The SDK splits those two axes on purpose — you can adopt one without the other.

    1. Layout — Form / FormSection / FormRow / FormActions handle how fields are arranged on screen.
    2. Validation — validateForm / zodResolver / useZodForm handle validating values with zod.

    Use them together or separately — the Form component is not coupled to any form library.

    Why zod as the source of truth?

    Instead of declaring the form's type and then writing validation rules that can drift from it, you write a single zod schema and the TypeScript type is inferred with z.infer. Schema and type never go out of sync, and the same rule runs on the client (validateForm/zodResolver) and on the server.

    Layout — Form + subcomponents

    Replaces the <form><Stack> boilerplate pattern when you want a layout-opinionated wrapper.

    import { Form, FormSection, FormRow, FormActions, Input, Select, Button } from "tempest-react-sdk";

    Where the examples' form comes from

    The snippets in this section are about layout, so they show the JSX only. The form you see in them (form.register, form.handleSubmit, form.formState) is react-hook-form's return value, created once at the top of the component:

    const form = useZodForm(schema, { defaultValues: { name: "", email: "" } });

    The first example below — Stacked — is complete, schema, imports and component included. See useZodForm for the hook and End-to-end example for a full form. If you already call useForm directly, const form = useForm({ resolver: zodResolver(schema) }) works just as well — Form is not coupled to any form library.

    layout variants

    layout Behavior
    "stack" (default) — flex column, gap = gap (default 4 → 16px).
    "inline" Flex row with flex-wrap: wrap + align-items: flex-end. Filter bars, short login, etc.
    "grid" display: grid with grid-template-columns: repeat(columns, minmax(0, 1fr)).

    columns accepts a number (repeat(N, minmax(0, 1fr))) or a string ("2fr 1fr", "min-content auto").

    gap accepts a number (4px scale: 2 → 8px, 4 → 16px) or a string (any CSS length: "1.5rem", "20px"). The number is a step, not pixels: gap={24} gives 96px, and in development a number above 12 warns once in the console — see gap={24} is not 24px.

    Stacked

    The default: one column, one field per row. This example is complete — copy, paste and run.

    import { Form, FormActions, Input, Button, useZodForm } from "tempest-react-sdk";
import { z } from "zod";

const signupSchema = z.object({
  name: z.string().min(2, "Enter your name"),
  email: z.string().email("Invalid email"),
  password: z.string().min(8, "At least 8 characters"),
});

type SignupValues = z.infer<typeof signupSchema>;

export function SignupForm() {
  const form = useZodForm(signupSchema, {
    defaultValues: { name: "", email: "", password: "" },
  });

  const onSubmit = async (values: SignupValues) => {
    await api.post("/signup", values);
  };

  return (
    <Form layout="stack" gap={4} onSubmit={form.handleSubmit(onSubmit)}>
      <Input label="Name" {...form.register("name")} error={form.formState.errors.name?.message} />
      <Input
        label="Email"
        type="email"
        {...form.register("email")}
        error={form.formState.errors.email?.message}
      />
      <Input
        label="Password"
        type="password"
        {...form.register("password")}
        error={form.formState.errors.password?.message}
      />
      <FormActions align="end">
        <Button type="submit" loading={form.formState.isSubmitting}>
          Create account
        </Button>
      </FormActions>
    </Form>
  );
}

    The examples below show the Form JSX only — form and onSubmit come from the same place as here.

    Grid

    <Form layout="grid" columns={2} gap={4} onSubmit={form.handleSubmit(onSubmit)}>
  <Input label="First name" {...form.register("name")} />
  <Input label="Last name" {...form.register("last_name")} />
  <Input label="Email" type="email" {...form.register("email")} />
  <Input label="Phone" {...form.register("phone")} />
  <FormActions align="end" style={{ gridColumn: "1 / -1" }}>
    <Button type="submit">Save</Button>
  </FormActions>
</Form>

    Full-row span

    Use gridColumn: "1 / -1" to make a field (or FormActions) span the whole grid row, regardless of how many columns there are.

    Inline

    A filter bar needs no form library at all — onSubmit here is the native <form> handler, which Form forwards straight through.

    const statusOptions = [
  { value: "active", label: "Active" },
  { value: "archived", label: "Archived" },
];

function handleFilter(event: React.FormEvent<HTMLFormElement>) {
  event.preventDefault();
  const data = new FormData(event.currentTarget);
  setFilters({ q: String(data.get("q") ?? ""), status: String(data.get("status") ?? "") });
}

<Form layout="inline" gap={2} onSubmit={handleFilter}>
  <Input name="q" label="Search" placeholder="name…" />
  <Select name="status" label="Status" options={statusOptions} />
  <Button type="submit">Filter</Button>
</Form>;

    Typical filter bars: align-items: flex-end keeps the buttons aligned with the inputs' baseline.

    FormSection — subgroups with independent layout

    <Form layout="stack" gap={5}>
  <Input label="Email" {...form.register("email")} />

  <FormSection title="Address" description="Used for delivery" layout="grid" columns={3} gap={3}>
    <Input label="ZIP" {...form.register("cep")} />
    <Input label="City" {...form.register("city")} />
    <Input label="State" {...form.register("state")} />
    <Input label="Street" style={{ gridColumn: "1 / -1" }} {...form.register("street")} />
  </FormSection>

  <FormActions align="end">
    <Button type="submit">Save</Button>
  </FormActions>
</Form>

    FormSection renders a <section> with a <header> (when title or description is present) + body. The body has its own layout / columns / gap.

    FormRow — side-by-side inside a stack

    <Form layout="stack" gap={4}>
  <Input label="Card number" />
  <FormRow gap={3}>
    <Input label="Expiry" placeholder="MM/YY" />
    <Input label="CVV" />
  </FormRow>
</Form>

    FormRow is always horizontal with flex-wrap: wrap. Children share the width equally (flex: 1 1 0).

    FormActions — footer buttons

    <FormActions align="between" gap={2}>
  <Button variant="ghost" type="button" onClick={onCancel}>
    Cancel
  </Button>
  <Button type="submit" loading={form.formState.isSubmitting}>
    Save
  </Button>
</FormActions>

    align: "start" / "center" / "end" (default) / "between".

    Validation — zod

    Three levels of zod integration, from lightest to most opinionated. The schema is the source of truth — the type is inferred.

    1. validateForm — agnostic

    Does not require react-hook-form. Useful for manual controlled forms or batch validation.

    import { validateForm } from "tempest-react-sdk";

const result = validateForm(schema, values);
if (!result.success) {
  setErrors(result.errors); // Record<path, message>
  return;
}
await save(result.data);

    Path in dot-notation ("address.city", "items.0.name"). Root errors: _root.

    First error per field wins

    validateForm keeps only the first issue per path in the error map — form UIs almost always show one message per field. If you need all the messages (e.g. a password-rules checklist), read schema.safeParse(values).error.issues directly.

    2. zodResolver — react-hook-form

    Replaces @hookform/resolvers/zod (no extra dependency).

    import { useForm } from "react-hook-form";
import { zodResolver } from "tempest-react-sdk";

const form = useForm({ resolver: zodResolver(loginSchema) });

    A field named like an Object.prototype member

    validateForm and zodResolver write each error as an own property and check it with hasOwnProperty. Before, a field named constructor or toString looked as if it already had an error (inherited from the prototype) and lost its message, and an issue a superRefine filed under __proto__ replaced the map's prototype instead of becoming a key.

    3. useZodForm — all-in-one

    const form = useZodForm(loginSchema, { defaultValues: { email: "", password: "" } });

<Form layout="stack" onSubmit={form.handleSubmit(login)}>
  <Input label="Email" {...form.register("email")} error={form.formState.errors.email?.message} />
  <Input
    label="Password"
    type="password"
    {...form.register("password")}
    error={form.formState.errors.password?.message}
  />
  <FormActions>
    <Button type="submit" loading={form.formState.isSubmitting}>
      Sign in
    </Button>
  </FormActions>
</Form>;

    Input and output — a required select that opens empty

    useZodForm types the form by both sides of the schema: the fields, defaultValues, watch and setValue by its input (z.input, what the input holds while the person edits), and handleSubmit by its output (z.output, what the parse returns). That is what lets a required select open empty without lying to the submit type:

    import { FormField, FormProvider, Select, toOptions, useZodForm } from "tempest-react-sdk";
import { z } from "zod";

const STATUS = { active: "Ativo", paused: "Pausado" };

const schema = z.object({
    status: z
        .union([z.enum(["active", "paused"]), z.literal("")])
        .refine((value) => value !== "", "Pick a status"),
    stock: z.coerce.number().int().min(0),
});

export function StatusForm({ onSave }: { onSave: (values: z.output<typeof schema>) => void }) {
    const form = useZodForm(schema, { defaultValues: { status: "", stock: "" } });
    return (
        <FormProvider {...form}>
            <form onSubmit={form.handleSubmit(onSave)} noValidate>
                <FormField name="status" label="Status" required>
                    <Select placeholder="Select" options={toOptions(STATUS)} />
                </FormField>
            </form>
        </FormProvider>
    );
}
    • status: "" compiles as an initial value because the schema's input accepts "".
    • value !== "" is a type predicate: the output keeps only "active" | "paused", and onSave never receives "".
    • stock holds the text the input typed (unknown on the input side) and reaches the submit as a number.

    Up to 0.92.0, both sides were the output

    With the fields typed by the output, defaultValues: { status: "" } did not compile, and the workaround (refine((value) => value.length > 0), no predicate) leaked "" into the type the submit receives. And the form type was inferred from defaultValues: { status: "" } typed the field as string and dropped the schema's enum. defaultValues is now NoInfer — the type comes from the schema only. Code that annotated its initial values with z.infer now annotates them with z.input.

    4. Server errors on the fields — applyApiFieldErrors

    FastAPI's 422 (or a tempest-fastapi-sdk error naming field) arrives as error.fields, { name: message }. applyApiFieldErrors puts each message on the form field with that name and focuses the first:

    import { useMutation } from "@tanstack/react-query";
import {
    FormField,
    FormProvider,
    Input,
    applyApiFieldErrors,
    createApiClient,
    useDescribeApiError,
    useToast,
    useZodForm,
} from "tempest-react-sdk";
import { z } from "zod";

const api = createApiClient({ baseURL: "/api" });
const schema = z.object({ name: z.string().min(3), email: z.email() });

export function CustomerForm() {
    const toast = useToast();
    const describe = useDescribeApiError();
    const form = useZodForm(schema, { defaultValues: { name: "", email: "" } });
    const save = useMutation({
        mutationFn: (values: z.output<typeof schema>) => api.post("/customers", { body: values }),
        onError: (error) => {
            const { marked, unmatched } = applyApiFieldErrors(form, error);
            const others = Object.values(unmatched);
            if (marked.length === 0) toast.error(describe(error, "Could not save."));
            else if (others.length > 0) toast.error(others.join(" "));
        },
    });
    return (
        <FormProvider {...form}>
            <form onSubmit={form.handleSubmit((values) => save.mutate(values))} noValidate>
                <FormField name="name" label="Name">
                    <Input />
                </FormField>
                <FormField name="email" label="E-mail">
                    <Input type="email" />
                </FormField>
            </form>
        </FormProvider>
    );
}
    • Only names of the form are marked. By default a name counts when form.getValues(name) is not undefined — every field with an initial value, which is how useZodForm is meant to be used. Pass { fields: [...] } to decide the list yourself.
    • The rest comes back in unmatched, keyed by name: an input that does not exist would never show the message, and it would stay stuck in an error nobody can clear.
    • { focus: false } marks without moving focus.
    • Any other error — network, 500, a plain Error — marks nothing and returns { marked: [], unmatched: {} }.

    It is the same code as AuthForm's

    The rule (mark only what exists, focus the first, return the rest) was private to AuthForm; every form outside it rewrote the setError loop — and the three recipes that rewrote it disagreed with each other. AuthForm now uses applyApiFieldErrors.

    End-to-end example — schema → provider → fields → submit

    The three snippets above are slices of the same story. Here is an end-to-end signup form: a single schema drives types, validation and <FormField> wires the RHF state into every control without a repeated <Controller>.

    import {
  Form,
  FormField,
  FormProvider,
  FormActions,
  Button,
  Input,
  useZodForm,
  type SubmitHandler,
} from "tempest-react-sdk";
import { z } from "zod";

// 1. Schema = source of truth. The SignupValues type is inferred from it.
const signupSchema = z
  .object({
    name: z.string().min(2, "Enter your name"),
    email: z.string().email("Invalid email"),
    password: z.string().min(8, "At least 8 characters"),
    confirm: z.string(),
  })
  .refine((data) => data.password === data.confirm, {
    message: "Passwords do not match",
    path: ["confirm"], // error attached to the "confirm" field
  });

type SignupValues = z.infer<typeof signupSchema>;

export function SignupForm() {
  // 2. useZodForm wires the zod resolver + infers SignupValues automatically.
  const form = useZodForm(signupSchema, {
    defaultValues: { name: "", email: "", password: "", confirm: "" },
  });

  // 4. handleSubmit only fires the submit once the schema passes.
  const onSubmit: SubmitHandler<SignupValues> = async (values) => {
    await fetch("/api/signup", {
      method: "POST",
      body: JSON.stringify(values),
    });
  };

  return (
    // 3. FormProvider exposes `control` to the tree; FormField reads it from context.
    <FormProvider {...form}>
      <Form layout="stack" gap={4} onSubmit={form.handleSubmit(onSubmit)}>
        <FormField name="name" label="Name" required>
          <Input />
        </FormField>
        <FormField name="email" label="Email" required>
          <Input type="email" />
        </FormField>
        <FormField name="password" label="Password" required>
          <Input type="password" />
        </FormField>
        <FormField name="confirm" label="Confirm password" required>
          <Input type="password" />
        </FormField>
        <FormActions align="end">
          <Button type="submit" loading={form.formState.isSubmitting}>
            Create account
          </Button>
        </FormActions>
      </Form>
    </FormProvider>
  );
}

    How the pieces fit together:

    • useZodForm(schema) returns react-hook-form's UseFormReturn object, with the zod resolver already plugged in. You get register, handleSubmit, formState, control, etc., typed against SignupValues.
    • <FormProvider {...form}> publishes that return value into RHF's context. This is what lets <FormField> find control on its own.
    • <FormField name="..." label="..."> wraps a <Controller> under the hood and uses cloneElement to inject value / onChange / onBlur / ref / error / aria-invalid into the child control. You pass a "dumb" <Input /> and FormField wires everything up.
    • form.handleSubmit(onSubmit) runs the schema first; onSubmit only ever receives already-validated, typed values.

    FormField removes the repeated <Controller>

    Without it, each controlled field becomes a 5-line <Controller name=... render={({ field, fieldState }) => ...} />. <FormField> does that render-prop once and forwards error + aria-invalid to the control automatically.

    FormField needs a control or a Provider

    <FormField> looks up control from the <FormProvider> context. If you don't want a provider, pass control={form.control} explicitly on each <FormField>. With neither, it throws "FormField requires either a control prop or a <FormProvider> in the tree.".

    The child control must accept the injected props

    <FormField> expects the child to accept value / onChange / onBlur / ref / error / label. The SDK components (Input, Select, and the BR masked inputs) already do — a raw DOM <input> does not understand error/label and will warn about unknown props.

    Cross-field errors

    Validations that depend on two fields (password × confirmation) go in a .refine() on the schema with path: ["field"] — that way the error shows up attached to the right field in formState.errors.

    react-hook-form comes out of the same barrel

    The SDK re-exports the react-hook-form hooks you would reach for alongside useZodForm, so a form file has one import:

    import {
  FormProvider,
  useFieldArray,
  useFormContext,
  useFormState,
  useWatch,
  useZodForm,
} from "tempest-react-sdk";
    Hook What it is for
    useFieldArray Dynamic list of fields (order lines, phone numbers) with append/remove.
    useFormContext Reaches the form from inside a child component, with no control prop threading.
    useWatch Watches a field re-rendering only the watcher, not the whole form.
    useFormState Reads errors/isDirty/isSubmitting with the same subscription granularity.

    These are the react-hook-form hooks, unwrapped: their documentation applies literally, and importing straight from react-hook-form behaves identically. The re-export exists so your app need not declare a dependency the SDK already ships.

    useWatch and useFormState exist for performance

    form.watch("field") and form.formState.errors re-render the component holding the form — on a large form that is the whole screen on every keystroke. These hooks subscribe to just the watched slice, in the component that watches it.

    \"FormField found no form to bind to\" with a <FormProvider> visible above it

    When this happens with the provider mounted right above, the cause is not what the sentence suggests: the app and the SDK are resolving two copies of react-hook-form. <FormProvider> publishes on one copy's context and the useFormContext inside <FormField> reads the other's, which is empty.

    Same mechanism as useNavigate() may be used only in the context of a <Router>, and it goes unnoticed for the same reason: nobody looks in node_modules while looking at the provider on screen. That is why the SDK's error message names both causes as of v0.52.1.

    Fix: npm dedupe, or npx tempest doctor to list the duplicates.

    Schema pattern

    Keep schemas in src/schemas/<domain>.ts, export the z.infer in src/types/<domain>.ts via declare global when you want global types. Convention inherited from alofans-frontend.

    Recap

    • The SDK splits layout (Form/FormSection/FormRow/FormActions) from validation (zod) — adopt one without the other.
    • Validation has three rungs: validateForm (agnostic), zodResolver (RHF), useZodForm (all-in-one).
    • useZodForm types the fields by the schema's input and handleSubmit by its output: a required select opens with "" and the submit only sees the enum.
    • applyApiFieldErrors(form, error) puts a 422's error.fields on the right fields and returns what matched nothing in unmatched.
    • A single zod schema drives the type (z.infer), validation, and error messages.
    • <FormProvider> + <FormField> remove the repeated <Controller> and propagate error + aria-invalid to the controls.
    • handleSubmit only calls your onSubmit with already-validated values.
