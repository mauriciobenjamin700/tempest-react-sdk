    Offline field app

    The co-op technician leaves town at 6 a.m., drives 80 km of dirt road and spends the day going from farm to farm. At every gate he does the same inspection: how many head of cattle, whether the water troughs are clean, whether the fence holds, whether vaccination is up to date. He takes photos. He writes down what the farmer said.

    There is no signal in the pasture. Sometimes a weak 2G shows up near the farmhouse and drops in the middle of an upload. Real signal only comes back at night, at the hotel in town.

    This recipe builds the app that technician uses: a PWA that works entirely without a network, keeps everything on the device and sends it on its own when signal shows up — photos included, which resume from where they stopped when the connection drops halfway. 🚜

    This recipe is about the field

    The sync engine itself (outbox, watermark, paginated pull) is explained piece by piece in Offline Sync (FastAPI). Here you see that engine working inside a real app, together with the camera, GPS, resumable upload and export.

    What we are going to build

    • Visit list — reads from the device, never from the network. Shows what has been sent, what is waiting for signal and what hit a conflict.
    • Inspection form — farm, farmer (with a validated CPF), herd size, checklist, notes and the GPS location, which works without internet.
    • Camera photos — downscaled and compressed on the device before they take up space, and sent by resumable upload when there is signal.
    • Sync status — the badge at the top, the "pending upload" panel and the offline bar.
    • Conflict — the supervisor approved the visit at the office while the technician was still editing it in the pasture. The app shows that and lets him choose.
    • Export the visit — an .xlsx sheet + photos in a .zip, built without a network, so the technician can send it to the farmer over WhatsApp.
    • PWA — opens without a network, asks for persistent storage and does not swap versions in the middle of an inspection.

    And the states every real screen has: loading, empty, error, success — and the phone screen, which is the only one that matters here.

    The backend contract

    The backend is a FastAPI service on top of tempest-fastapi-sdk, following its offline-sync recipe. The app talks to four routes, all under root_path="/api":

    Route What it does
    PUT /api/visits/{id} Idempotent upsert of the visit. The id is generated on the device.
    GET /api/visits/changes?since&cursor&limit Paginated delta since the last server_time.
    GET /api/visits/{id} The server's version, used to resolve a conflict.
    POST /api/uploads (tus) Resumable upload of the photos.

    tus server on the backend

    The /api/uploads route needs a tus server. From 0.370.0 on, tempest-fastapi-sdk ships one (make_tus_router), which binds each upload to its owner through current_user_id — what matters on a shared tablet. On a backend without it, tusd behind the same proxy is the common path. The table of what the server must answer is in Resumable upload.

    The code, file by file

    1. The model

    // src/visits/types.ts
export type VisitStatus = "draft" | "done" | "approved";

export type VisitSyncState = "pending" | "synced" | "conflict";

export interface VisitChecklist {
  water: boolean;
  fences: boolean;
  vaccination: boolean;
  pasture: boolean;
}

export interface Visit {
  id: string;
  technician_id: string;
  farm_name: string;
  producer_name: string;
  producer_cpf: string;
  herd_size: number;
  checklist: VisitChecklist;
  notes: string;
  status: VisitStatus;
  latitude: number | null;
  longitude: number | null;
  visited_at: string;
  updated_at: string;
  sync_state: VisitSyncState;
  conflict_detail: string | null;
}

export interface VisitPhoto {
  id: string;
  visit_id: string;
  technician_id: string;
  blob: Blob | null;
  thumb: Blob;
  bytes: number;
  taken_at: string;
  upload_url: string | null;
}

export interface PhotoRef {
  id: string;
  url: string;
  taken_at: string;
}

export interface VisitDto extends Omit<Visit, "sync_state" | "conflict_detail"> {
  photos: PhotoRef[];
  is_deleted: boolean;
}

export type VisitPayload = Omit<VisitDto, "is_deleted">;

export interface VisitChangesPage {
  items: VisitDto[];
  next_cursor: string | null;
  has_more: boolean;
  limit: number;
  server_time: string;
}

export function fromDto(dto: VisitDto): Visit {
  return {
    id: dto.id,
    technician_id: dto.technician_id,
    farm_name: dto.farm_name,
    producer_name: dto.producer_name,
    producer_cpf: dto.producer_cpf,
    herd_size: dto.herd_size,
    checklist: dto.checklist,
    notes: dto.notes,
    status: dto.status,
    latitude: dto.latitude,
    longitude: dto.longitude,
    visited_at: dto.visited_at,
    updated_at: dto.updated_at,
    sync_state: "synced",
    conflict_detail: null,
  };
}

export function toPayload(visit: Visit, photos: PhotoRef[]): VisitPayload {
  return {
    id: visit.id,
    technician_id: visit.technician_id,
    farm_name: visit.farm_name,
    producer_name: visit.producer_name,
    producer_cpf: visit.producer_cpf,
    herd_size: visit.herd_size,
    checklist: visit.checklist,
    notes: visit.notes,
    status: visit.status,
    latitude: visit.latitude,
    longitude: visit.longitude,
    visited_at: visit.visited_at,
    updated_at: visit.updated_at,
    photos,
  };
}

    Three things to notice:

    • The id is born on the device (crypto.randomUUID()). That is what makes the PUT a safe upsert: sending the same visit twice does not create two.
    • sync_state and conflict_detail are local only — the server never sees them. They tell the screen whether the visit is waiting for signal, already went, or hit a conflict.
    • The photo keeps the Blob itself, not a URL. There is no server to point at in the pasture. Once it is uploaded, blob becomes null and only the thumbnail (thumb) stays: the device does not keep what the server already has.

    2. The session

    // src/lib/auth.ts
import { createTempestAuth, requestPersistentStorage } from "tempest-react-sdk";

export interface Technician {
  id: string;
  name: string;
  email: string;
}

export const auth = createTempestAuth<Technician>({
  baseURL: import.meta.env.VITE_API_URL,
  prefix: "/api",
  mePath: "/auth/me",
});

export function currentTechnicianId(): string | null {
  return auth.useAuthStore.getState().user?.id ?? null;
}

export async function signIn(email: string, password: string): Promise<void> {
  await auth.login({ email, password });
  void requestPersistentStorage();
}

    createTempestAuth wires login, refresh and an already-authenticated auth.api. currentTechnicianId is read outside React — by the sync engine and the database — so it is a function, not a hook.

    signIn asks for persistent storage right after login. Without it, the browser may delete IndexedDB under disk pressure — and in Safari outside the home screen, after ~7 days without use. The request lives here, not in the sync engine, because in Firefox it opens a permission prompt: at login the technician understands why the app is asking; in the middle of a background upload, they do not.

    3. The on-device database

import { createOfflineDatabase } from "tempest-react-sdk";
import type { Visit, VisitPhoto } from "@/visits/types";

const database = createOfflineDatabase<{ visits: Visit; photos: VisitPhoto }>({
  databaseName: "CampoVisitas",

    },

    },
  },

    Visits and photos live in the same database, through createOfflineDatabase. They belong to each other: you read, delete and migrate them together.

    ownerField: "technician_id" makes every put/list honour the owner. When two technicians share the same co-op tablet, one does not see the other's visits.

    Changed an index? Bump the version

    Changing indexes without bumping version breaks opening the database. Details in Offline › Migrations.

    4. The sync engine — with the photos inside

    This is the heart of the app.

    // src/visits/sync.ts
import { createOfflineSync, encodeIdSegment, isApiError, lastWriteWins } from "tempest-react-sdk";
import { auth, currentTechnicianId } from "@/lib/auth";
import { photos, visits } from "@/visits/db";
import { listPhotos } from "@/visits/photos";
import {
  fromDto,
  toPayload,
  type PhotoRef,
  type Visit,
  type VisitChangesPage,
  type VisitDto,
} from "@/visits/types";

const PHOTO_CHUNK_SIZE = 256 * 1024;

export const visitSync = createOfflineSync<Visit, VisitDto>({
  databaseName: "CampoVisitasOutbox",
  watermark: { storageKey: "campo.visits.watermark" },
  getPrincipal: currentTechnicianId,
  foreignEntries: "hold",
  coalesce: true,

  attachments: {
    list: async (entry) =>
      (await listPhotos(entry.recordId)).map((photo) => ({
        id: photo.id,
        blob: photo.blob,
        uploadedUrl: photo.upload_url,
      })),
    upload: (photo) => ({
      endpoint: auth.api.url("/uploads"),
      chunkSize: PHOTO_CHUNK_SIZE,
      metadata: { photo_id: photo.id, filetype: photo.blob.type },
      getToken: auth.getToken,
    }),
    onUploaded: async (photo, url) => {
      await photos.update(photo.id, { upload_url: url, blob: null });
    },
  },

  deliver: async (entry) => {
    const visit = entry.payload;
    if (visit === undefined) return;

    const takenAt = new Map(
      (await listPhotos(entry.recordId)).map((photo) => [photo.id, photo.taken_at]),
    );
    const photoRefs: PhotoRef[] = (entry.attachments ?? []).map((ref) => ({
      ...ref,
      taken_at: takenAt.get(ref.id) ?? visit.visited_at,
    }));

    try {
      await auth.api.put(`/visits/${encodeIdSegment(entry.recordId)}`, {
        body: toPayload(visit, photoRefs),
      });
    } catch (error) {
      if (isApiError(error) && error.status === 409 && error.code === "VISIT_LOCKED") {
        await visits.update(entry.recordId, {
          sync_state: "conflict",
          conflict_detail: error.detail,
        });
        return;
      }
      throw error;
    }

    const local = await visits.get(entry.recordId);
    if (local?.updated_at === visit.updated_at) {
      await visits.update(entry.recordId, { sync_state: "synced" });
    }
  },

  pullPage: async (since, cursor) => {
    const page = await auth.api.get<VisitChangesPage>("/visits/changes", {
      params: { since: since ?? undefined, cursor: cursor ?? undefined, limit: 100 },
    });
    return {
      items: page.items,
      nextCursor: page.has_more ? page.next_cursor : null,
      serverTime: page.server_time,
    };
  },

  applyRemote: async (dto) => {
    const owner = currentTechnicianId();
    if (owner === null) return;

    const local = await visits.get(dto.id);
    if (dto.is_deleted) {
      if (local?.sync_state !== "pending") await visits.delete(dto.id);
      return;
    }

    const remote = fromDto(dto);
    if (local?.sync_state === "pending") {
      const winner = lastWriteWins(local, remote, (visit) => visit.updated_at);
      if (winner === local) return;
    }
    await visits.put(remote, owner);
  },
});

export async function saveVisit(visit: Visit): Promise<void> {
  const owner = currentTechnicianId();
  if (owner === null) throw new Error("Sua sessão expirou. Entre de novo para salvar.");

  const existing = await visits.get(visit.id);
  const record: Visit = {
    ...visit,
    technician_id: owner,
    updated_at: new Date().toISOString(),
    sync_state: "pending",
    conflict_detail: null,
  };

  await visits.put(record, owner);
  await visitSync.enqueue(existing === undefined ? "create" : "update", record.id, record);
  void visitSync.flush("after-mutation");
}

export async function acceptServerVersion(visitId: string): Promise<void> {
  const owner = currentTechnicianId();
  if (owner === null) return;

  const dto = await auth.api.get<VisitDto>(`/visits/${encodeIdSegment(visitId)}`);
  await visits.put(fromDto(dto), owner);
}

    Let's go piece by piece. 🔍

    saveVisit: the device first, the network later

    saveVisit writes to IndexedDB, puts the visit in the outbox and asks for a flush. None of those three things needs a network. Without signal, the flush skips itself (summary.skipped) and the entry waits — the screen has already answered.

    create/update is just a label: since the route is an upsert, both become the same PUT.

    And coalesce: true folds the edits: a technician who saves the same visit ten times without signal sends one PUT when the network returns, with the newest version — not ten. The photos go up once either way (one that already has an upload_url is not sent again), but without the option every intermediate PUT still spent a round-trip on a signal that barely holds. Details, and what is not folded, in Ten edits, one request.

    attachments: the photos go up before the visit

    The photos are attachments of the visit. With the attachments option, createOfflineSync does this for each entry, in this order:

    1. Asks list which photos the visit has. They live in the app's store — the outbox keeps no copy of the file.
    2. Uploads the ones with no upload_url yet, one by one, with createResumableUpload and the options upload returns.
    3. Calls onUploaded for each, which stores the URL and swaps blob for null: the photo is on the server now, and the device keeps only the thumbnail.
    4. Calls deliver with the URLs in entry.attachments, and it sends the visit's PUT.

    Why don't the photos go in an outbox entry of their own? Because each photo would be another record, and the engine only orders entries of the same record — a failing record never holds up the others. The photo would fail on 2G, and the visit's PUT would reach the server pointing at a photo that does not exist. As attachments, they inherit everything the engine already does:

    • If anything fails — photo 3 of 5, or the PUT — the entry stays queued with attempts bumped, and the next flush tries again. With the photo failing, deliver is not even called.
    • Photos 1 and 2 already got an upload_url and do not go up again.
    • Photo 3 resumes from the byte where it stopped: the default key is outbox-attachment:<id>, the same on every flush, so the resumable upload finds its record and continues with a HEAD + PATCH.
    • Per-record order is preserved: a visit that failed does not let its next edit jump ahead. Other visits carry on normally.
    • A visit held for another technician (foreignEntries: "hold") uploads no photo.

    deliver only joins each photo's taken_at to the URLs, for the body the backend expects.

    Why the key carries the photo id

    The resumable upload's default fingerprint uses the File's name and lastModified. A Blob read from IndexedDB has neither, so two blobs of the same size would collide. That is why the engine's default key is outbox-attachment:<id>: each photo has its own resume point. See Resuming after a reload.

    Small chunks for bad signal

    The resumable upload default is DEFAULT_CHUNK_SIZE (5 MiB), bigger than a whole compressed photo. With chunkSize: 256 * 1024, a signal drop loses at most a small piece. The cost is more round-trips — which is the trade you want on a 2G that drops.

    getToken: auth.getToken is not an accident: with createTempestAuth's own getter, the resume point is bound to the session. If another technician signs in on the tablet, they do not resume the previous one's upload. Details in getToken: auth.getToken.

    getPrincipal: the shared tablet

    With getPrincipal, every outbox entry is stamped with whoever created it. Before each delivery the engine checks again:

    Who is signed in at delivery What happens
    the same technician delivered
    nobody stays queued until they come back
    another technician stays queued, unsent, until its owner is back

    The third row is foreignEntries: "hold". It keeps the server from receiving Carlos's inspection with Ana's token and keeps Carlos's work: if he signs out with pending visits and Ana signs in and syncs, his visits stay on the tablet and go out when he signs back in. The engine default ("drop") would delete them — it suits a personal device, not the cooperative's tablet. Details in Offline Sync › Shared device.

    A visit of Carlos's that Ana edits waits for his edit to go out first: per-record order holds for held entries too.

    pullPage and applyRemote: what comes from the office

    The pull brings what changed on the server since the last server_time. pullPage only translates the shape: has_more becomes nextCursor: null when the pages run out.

    applyRemote decides the conflict, and the rule is simple:

    • Local visit already sent (synced or conflict)? The server's replaces it.
    • Local visit pending? The most recent by updated_at wins, through lastWriteWins. If the local one is newer, it stays, and the next flush sends it.
    • Tombstone (is_deleted)? Delete — unless there is a pending local edit.

    The 409 VISIT_LOCKED: a conflict the machine does not settle

    The supervisor approved the visit at the office. The technician, offline, still fixed the head count. When the PUT arrives, the server refuses with 409 VISIT_LOCKED.

    Retrying does not help — the fifth attempt gets the same answer. So deliver does not throw: it marks the local visit as conflict, keeps the server's sentence and resolves. The entry leaves the queue, and the decision goes to whoever can make it: the technician, on screen. acceptServerVersion fetches the office's version and writes it over the local one.

    Variant: conflict by version instead of the clock

    updated_at comes from the device clock. A tablet with the wrong date (a battery that went flat, a wrong time zone) makes an old edit look new. If your backend keeps a version counter it increments on every write, extract the rule into a pickWinner and swap the comparison:

    // src/visits/conflict.ts
import { lastWriteWins } from "tempest-react-sdk";
import type { Visit } from "@/visits/types";

export function pickWinner(local: Visit, remote: Visit): Visit {
  return lastWriteWins(local, remote, (visit) => visit.updated_at);
}

    // src/visits/conflict.ts
import { higherVersionWins } from "tempest-react-sdk";

export interface VersionedVisit {
  id: string;
  version: number;
}

export function pickWinner<T extends VersionedVisit>(local: T, remote: T): T {
  return higherVersionWins(local, remote, (visit) => visit.version);
}

    In applyRemote, replace lastWriteWins(...) with pickWinner(local, remote). In both, a tie goes to the server.

    5. Photos on the device

    // src/visits/photos.ts
import type { CompressedImage, ProcessedImage } from "tempest-react-sdk/imaging";
import { currentTechnicianId } from "@/lib/auth";
import { photos } from "@/visits/db";
import type { VisitPhoto } from "@/visits/types";

export async function addPhoto(
  visitId: string,
  image: CompressedImage,
  thumb: ProcessedImage,
): Promise<VisitPhoto> {
  const owner = currentTechnicianId();
  if (owner === null) throw new Error("Sua sessão expirou. Entre de novo para fotografar.");

  const photo: VisitPhoto = {
    id: crypto.randomUUID(),
    visit_id: visitId,
    technician_id: owner,
    blob: image.blob,
    thumb: thumb.blob,
    bytes: image.bytes,
    taken_at: new Date().toISOString(),
    upload_url: null,
  };
  await photos.put(photo, owner);
  return photo;
}

export function listPhotos(visitId: string): Promise<VisitPhoto[]> {
  const owner = currentTechnicianId();
  if (owner === null) throw new Error("Your session expired. Sign in again to see the photos.");
  return photos.listBy("visit_id", visitId, owner, { orderBy: "taken_at" });
}

    listBy goes through the visit_id index and stays bound to the owner: calling photos.raw.where("visit_id") on Dexie directly also used the index, but returned another technician's photo for the same visit. With nobody signed in, the function throws instead of calling listBy without an owner — which would list everyone's photos.

    The photo enters the database with upload_url: null. Whoever sends it to the server is the sync engine, before deliver, the next time the visit syncs.

export function useVisitList(): UseQueryResult<Visit[], Error> {
  const technicianId: string | null = auth.useAuthStore((state) => state.user?.id ?? null);

  return useQuery({
    queryKey: ["visits", "list", technicianId],
    enabled: technicianId !== null,
    networkMode: "always",
    queryFn: () =>
      visits.list(technicianId ?? undefined, { orderBy: "visited_at", reverse: true }),
  });
}

export function useVisit(visitId: string): UseQueryResult<Visit | null, Error> {
  return useQuery({
    queryKey: ["visits", "one", visitId],
    networkMode: "always",
    queryFn: async () => (await visits.get(visitId)) ?? null,
  });
}

export function useVisitPhotos(visitId: string): UseQueryResult<VisitPhoto[], Error> {
  return useQuery({
    queryKey: ["visits", "photos", visitId],
    networkMode: "always",
    queryFn: () => listPhotos(visitId),
  });
}

    Without networkMode: \"always\", the list stays loading forever in the pasture

    TanStack Query pauses queries while the browser is offline — the default is networkMode: "online". Here the queryFn reads IndexedDB, which needs no network at all, but the query never even runs: the screen sits on the skeleton until signal comes back. networkMode: "always" tells Query this function does not depend on the network. The measurement, and why the SDK does not change the default for the whole client, are in Query → networkMode.

export function VisitPhotos({ visitId, disabled }: { visitId: string; disabled: boolean }) {
  const client = useQueryClient();
  const toast = useToast();
  const list = useVisitPhotos(visitId);
  const { compress, isWorking } = useImageProcessing();

  async function handleFiles(files: File[]): Promise<void> {
    const type = await bestSupportedType(["image/webp", "image/jpeg"]);

    for (const file of files) {
      try {
        const image = await compress(file, {
          maxBytes: 400_000,
          width: 1600,
          height: 1600,
          fit: "contain",
          withoutEnlargement: true,
          type,
        });
        const thumb = await resizeImage(image.blob, { width: 480, type });
        await addPhoto(visitId, image, thumb);
      } catch (error) {
        if (error instanceof StorageFullError) {
          toast.error("Memória cheia. Sincronize as visitas antes de tirar mais fotos.");
          break;
        }
        toast.error("Não deu para processar a foto. Tente fotografar de novo.");
      }
    }
    await client.invalidateQueries({ queryKey: ["visits", "photos", visitId] });
  }

  return (
    <section>
      <Dropzone
        accept="image/*"
        capture="environment"
        disabled={disabled || isWorking}
        onDrop={(files) => void handleFiles(files)}
      >
        <Camera size={18} aria-hidden /> {isWorking ? "Processando a foto…" : "Tirar foto"}
      </Dropzone>

      {list.isPending ? (
        <Skeleton height={96} style={{ marginTop: 12 }} />
      ) : list.isError ? (
        <p role="alert">Não deu para ler as fotos deste aparelho.</p>
      ) : list.data.length === 0 ? (
        <EmptyState
          title="Nenhuma foto"
          description="Fotografe bebedouros, cercas e o que mais o produtor precisar ver."
        />
      ) : (
        <div
          style={{
            display: "grid",
            gridTemplateColumns: "repeat(auto-fill, minmax(96px, 1fr))",
            gap: 8,
            marginTop: 12,
          }}
        >
          {list.data.map((photo) => (
            <PhotoThumb key={photo.id} photo={photo} />
          ))}
        </div>
      )}
    </section>
  );
}

    The Dropzone's capture="environment" opens the phone's own camera app, on the rear camera. You get focus, flash and full resolution without asking for any permission — and it works on the iPhone, where not every browser opens the camera inside the page. On desktop the same tap opens the file picker, and dragging a photo onto the area works too.

    A photo from a current phone is several MB. Storing that raw would fill the device in a few days. So it goes through useImageProcessing first:

    • width/height 1600 with fit: "contain" — downscaling is what saves the most;
    • maxBytes: 400_000 — compress searches for the quality that fits the budget;
    • bestSupportedType — WebP where the browser can encode it, JPEG where it cannot. Asking a browser that cannot encode WebP for it would return a PNG, several times bigger, with no error at all.
    • resizeImage with width: 480 makes the grid's thumbnail. It stays on the device after the upload, when onUploaded releases the full photo.

    Compressing before the put is the cheapest lever against the browser's storage limit: each photo takes up the device until it uploads, and in the field that can be days.

    useImagePreview creates the Blob's preview URL and revokes it on its own at unmount.

    When the device runs out of space, photos.put rejects with StorageFullError, and the loop stops: the next photos would not fit either, and the right message is "sync", not "shoot again". The browser's raw error would not even say that — in Chromium it arrives as Dexie's AbortError.

    Re-encoding drops the photo's GPS

    EXIF is gone after the re-encode, coordinates included. That protects the location of whoever takes the photo — but in an inspection you want to know where the photo was taken. That is why the location goes in the visit record, through useGeolocation, just below. See Imaging › Re-encoding drops EXIF.

function VisitForm({ initial, isNew }: { initial: Visit; isNew: boolean }) {

  const locked = draft.status === "approved";

  useEffect(() => {
    if (coords === null) return;

      current.latitude === null

      ["Bebedouros limpos e com água", yesNo(visit.checklist.water)],
      ["Cercas e porteiras em bom estado", yesNo(visit.checklist.fences)],
      ["Vacinação em dia", yesNo(visit.checklist.vaccination)],
      ["Pastagem sem degradação", yesNo(visit.checklist.pasture)],
      ["Latitude", visit.latitude],
      ["Longitude", visit.longitude],
      ["Observações", visit.notes],
      ["Fotos", photoList.length],
    ],
  );

  return createZip(
    [
      { path: "visita.xlsx", data: sheet },
      ...photoList.map((photo, index) => ({
        path: `fotos/foto-${String(index + 1).padStart(2, "0")}.${extensionOf((photo.blob ?? photo.thumb).type)}`,
        data: photo.blob ?? photo.thumb,
      })),
    ],
    {
      onProgress: ({ loaded, total }) =>
        onPercent(total === 0 ? 100 : Math.round((loaded / total) * 100)),
    },
  );
}

    // src/components/ExportVisitButton.tsx
import { Share2 } from "lucide-react";
import { useState } from "react";
import { Button, Progress, shareOrDownloadBlob, useToast } from "tempest-react-sdk";
import { buildVisitZip } from "@/visits/export";
import type { Visit } from "@/visits/types";

export function ExportVisitButton({ visit }: { visit: Visit }) {
  const toast = useToast();
  const [percent, setPercent] = useState<number | null>(null);
  const [zip, setZip] = useState<Blob | null>(null);

  async function generate(): Promise<void> {
    setPercent(0);
    try {
      setZip(await buildVisitZip(visit, setPercent));
    } catch {
      toast.error("Não deu para montar o arquivo da visita.");
    } finally {
      setPercent(null);
    }
  }

  async function share(file: Blob): Promise<void> {
    await shareOrDownloadBlob(file, `visita-${visit.id.slice(0, 8)}.zip`, {
      title: `Visita — ${visit.farm_name}`,
    });
    setZip(null);
  }

  if (percent !== null) {
    return <Progress value={percent} showLabel label="Montando o arquivo" />;
  }
  if (zip !== null) {
    return (
      <Button size="sm" leftIcon={<Share2 size={16} />} onClick={() => void share(zip)}>
        Compartilhar
      </Button>
    );
  }
  return (
    <Button size="sm" variant="outline" onClick={() => void generate()}>
      Exportar
    </Button>
  );
}
    • writeXlsx builds the sheet in memory. Numbers go in as numbers (Excel sums them), null becomes an empty cell, accents survive.
    • createZip builds the archive in slices, without freezing the screen, and stores the photos without recompressing — they are already WebP/JPEG. onProgress feeds the Progress.
    • A photo that already went up goes in as its thumbnail: the full one left the device in onUploaded. In the pasture, before signal, the ZIP carries the full photos.
    • shareOrDownloadBlob opens the phone's share sheet (WhatsApp, e-mail, Drive) and downloads on desktop.

    Why two taps: \"Exportar\" and then \"Compartilhar\"

    The browser only opens the share sheet right after a user tap (the transient activation). Building a ZIP with ten photos takes time, and by the end of it that window may have closed — then navigator.share refuses and shareOrDownloadBlob falls back to a download. Splitting "build" from "share" makes the second tap open the sheet right away.

    The ZIP carries the farmer's CPF

    Personal data leaving the app over WhatsApp is processing of personal data under the LGPD (Brazil's data protection law). Confirm with the co-op's legal team that the farmer receives their own report and that this is an intended use. If you do not need the CPF in the sheet, drop the row.

    // src/App.tsx
import { useQueryClient } from "@tanstack/react-query";
import { useEffect } from "react";
import { BrowserRouter, Route, Routes } from "react-router";
import {
  Banner,
  Button,
  OfflineIndicator,
  formatBytes,
  QueryProvider,
  ToastProvider,
  UpdatePrompt,
  useOfflineSync,
  useServiceWorkerUpdate,
  useStorageEstimate,
} from "tempest-react-sdk";
import { VisitFormPage } from "@/pages/VisitFormPage";
import { VisitListPage } from "@/pages/VisitListPage";
import { visitSync } from "@/visits/sync";

function SyncRunner() {
  const client = useQueryClient();
  useOfflineSync(visitSync, { flushOnMount: true, flushOnOnline: true, intervalMs: 120_000 });

  useEffect(
    () =>
      visitSync.subscribe(() => {
        void client.invalidateQueries({ queryKey: ["visits"] });
      }),
    [client],
  );

  return null;
}

function StorageGuard() {
  const storage = useStorageEstimate({ pollMs: 60_000 });
  const { pending, pendingBytes } = useOfflineSync(visitSync, { flushOnOnline: false });

  if (storage.persisted === false && pending > 0) {
    return (
      <Banner
        variant="warning"
        title="Proteja as visitas deste aparelho"
        action={<Button size="sm" onClick={() => void storage.requestPersist()}>Proteger</Button>}
      >
        {formatBytes(pendingBytes)} em fotos ainda não foram enviadas. Sem proteção, o navegador
        pode apagá-las quando faltar espaço.
      </Banner>
    );
  }
  if (storage.ratio !== null && storage.ratio > 0.8) {
    return (
      <Banner variant="danger" title="Armazenamento quase cheio">
        {formatBytes(storage.usage)} de {formatBytes(storage.quota)} usados,{" "}
        {formatBytes(pendingBytes)} esperando envio. Envie as visitas pendentes antes de tirar
        mais fotos.
      </Banner>
    );
  }
  return null;
}

function ServiceWorkerGate() {
  const { updateAvailable, applyUpdate } = useServiceWorkerUpdate({ url: "/sw.js" });
  return <UpdatePrompt open={updateAvailable} onUpdate={applyUpdate} />;
}

export function App() {
  return (
    <QueryProvider>
      <ToastProvider position="top-center">
        <BrowserRouter>
          <OfflineIndicator position="top" />
          <StorageGuard />
          <SyncRunner />
          <Routes>
            <Route path="/" element={<VisitListPage />} />
            <Route path="/visitas/:visitId" element={<VisitFormPage />} />
          </Routes>
          <ServiceWorkerGate />
        </BrowserRouter>
      </ToastProvider>
    </QueryProvider>
  );
}

import { installPrecache, installSkipWaitingListener } from "tempest-react-sdk/sw";

installSkipWaitingListener();

installPrecache({
  navigateFallback: "/index.html",
  navigateFallbackDenylist: [/^\/api\//],

    • SyncRunner is the only place that triggers the upload: at boot, when the network comes back and every two minutes. flush is single-flight, so triggers that coincide become one run. On every engine change it invalidates the ["visits"] queries, and the list shows the new badge without a reload.
    • StorageGuard joins useStorageEstimate (how much the device uses and holds) with the engine's pendingBytes (how much of that is work that does not exist anywhere else yet). Without persistent storage the browser may evict IndexedDB under disk pressure; signIn already asked for protection, and the banner only shows when it was denied and something is pending.
    • OfflineIndicator shows the offline bar and flashes a confirmation when signal comes back.
    • UpdatePrompt asks before swapping versions. Reloading on its own in the middle of an inspection would wipe what is typed in the form.
    • sw.ts only precaches the app shell, so the app opens without a network. See PWA.

    Why this sw.ts has no installBackgroundSync

    In this app, the outbox is what resends, and the tus upload resumes by itself. The --pwa template already keeps tus out of background sync; if you keep the scaffold's installBackgroundSync, add "/api/visits/" to RETRIED_BY_THE_PAGE in src/sw-sync-scope.ts, or a PUT /api/visits/… that failed offline goes out of both queues. See One queue per mutation.

    Testing in the field (without going to the field)

    1. Open the app in Chrome, sign in and let the service worker install.
    2. DevTools → Network → Offline. Create two visits with photos. The list shows "Não enviada"; the badge at the top, "Offline".
    3. Reload the page while still offline. Everything is still there — the app shell from the precache, the data from IndexedDB. ✅
    4. Switch to Slow 3G and save. While a photo is uploading, go back to Offline and then to Slow 3G. In the Network tab, the upload resumes with a HEAD followed by a PATCH from the offset — not a new POST.

    Recap

    • 🗄️ createOfflineDatabase keeps visits and photos (as Blobs) in the same database, owned per technician.
    • 📤 createOfflineSync is the outbox: saveVisit writes locally and enqueues; the upload happens whenever it can, and coalesce: true folds the edits of one visit into a single PUT.
    • 📸 Photos are the visit's attachments: the engine uploads them with the resumable upload before deliver — a failure retries, a drop resumes from the offset, a sent photo does not go up again, and onUploaded frees the file from the device.
    • ⚖️ Conflicts come in two kinds: the one the machine settles (lastWriteWins in applyRemote) and the one the technician settles (409 VISIT_LOCKED becomes the conflict state on screen).
    • 🗜️ useImageProcessing + bestSupportedType shrink the photo on the device; GPS goes in the record, because the re-encode drops EXIF.
    • 🟢 SyncStatusBadge, useOfflineSync and OfflineIndicator tell the technician what is going on; with foreignEntries: "hold", signing out never risks the queue.
    • 📦 writeXlsx + createZip + shareOrDownloadBlob deliver the report without a network.
    • 💾 StorageFullError tells "storage full" apart from "bad photo" in the camera's catch.
    • 🔒 Login asks for persistent storage; useStorageEstimate + pendingBytes warn when space runs short; UpdatePrompt does not swap versions mid-inspection; the service worker only precaches.
    • ⚠️ networkMode: "always" on the queries that read IndexedDB, or they pause offline.
