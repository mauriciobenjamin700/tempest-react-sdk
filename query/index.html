    Query (TanStack Query)

    Wrappers finos pra padronizar tempos de cache, chaves de query e o QueryClient. Você continua usando o @tanstack/react-query de sempre — o SDK só entrega os defaults bem calibrados e um factory de keys tipado.

    Por que esses wrappers existem?

    Sem padronização, cada tela escolhe um staleTime no chute e cada domínio escreve queryKey: ["user", id] à mão. Isso gera invalidações que não pegam (key montada diferente em dois lugares) e refetch agressivo demais. O SDK centraliza ambos: presets nomeados e um factory que garante a mesma key em todo lugar.

    Seção recipe-query da gallery — rode localmente para interagir.

    Provider

    Envolva a árvore do app uma única vez, normalmente no main.tsx (ou dentro de <AppProviders>):

    import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { QueryProvider } from "tempest-react-sdk";
import "tempest-react-sdk/styles.css";
import { App } from "./App";

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <QueryProvider>
      <App />
    </QueryProvider>
  </StrictMode>,
);

    Defaults aplicados quando você não passa um client:

    • staleTime: 5 min (STALE_TIME.DEFAULT)
    • gcTime: 30 min (CACHE_TIME.DEFAULT)
    • retry: shouldRetryQuery (queries) / 0 (mutations)
    • refetchOnWindowFocus: false

    4xx não é retentado — e isso mudou

    O default era retry: 1 chapado, que replicava um 403 numa listagem admin-only e um 404 de registro apagado. O servidor recusou de propósito nos dois casos: a segunda tentativa devolve a mesma resposta, dobra o log de rede e segura o spinner na tela por mais um round trip.

    shouldRetryQuery retenta uma vez apenas o que pode mudar sozinho: falha de rede (status === 0), 5xx, 408, 425 e 429 (que é uma recusa cujo significado literal é "mais tarde"), e erro de formato desconhecido — que pode ser falha de transporte. Todo o resto do 4xx falha de primeira.

    A classificação vem de isRetriableStatus, a mesma que createApiClient({ retry: true }) e o helper retry() usam. Até a v0.44.0 era uma cópia própria aqui, sem o 425 — então o mesmo 425 Too Early era retentado pelo cliente e não pela query.

    Se o seu app dependia de retry em 4xx, o override é o de sempre: defaultOptions={{ queries: { retry: 1 } }}.

    Para sobrescrever, passe defaultOptions (mesclado por cima dos defaults) ou um client pronto. Um client feito com new QueryClient() ignora os defaults do SDK; feito com createQueryClient(), ele os mantém:

    import { createQueryClient, QueryProvider, STALE_TIME } from "tempest-react-sdk";

// Opção A — só ajustar alguns defaults
<QueryProvider defaultOptions={{ queries: { staleTime: STALE_TIME.LONG } }}>
  <App />
</QueryProvider>;

// Opção B — trazer seu próprio client (compartilhar entre roots, plugar devtools, etc.)
const client = createQueryClient();
<QueryProvider client={client}>
  <App />
</QueryProvider>;

    Um único QueryClient por app

    Não aninhe dois QueryProvider sem passar o mesmo client. Cada provider cria um cache isolado, e queries de subárvores diferentes deixam de compartilhar dados. Para múltiplos roots, crie o QueryClient uma vez e passe via prop client.

    \"No QueryClient set\" com o provider montado = duas cópias do react-query

    O client que você passa é o único ponto onde a cópia do app e a do SDK se encostam. Se o npm aninhou uma segunda cópia de @tanstack/react-query dentro do SDK, o QueryClientProvider publica o seu client no contexto daquela cópia — e todo useQuery do app lê o contexto da outra, não acha nada, e lança:

    No QueryClient set, use QueryClientProvider to set one

    Com o provider visivelmente montado três linhas acima. Nada nessa mensagem aponta pra duplicata, e é por isso que ela custa uma tarde.

    A partir da v0.52.1 o SDK detecta e avisa em desenvolvimento: um client de outra cópia faz duck-type perfeito mas falha o instanceof, que é a discriminação exata. O conserto é npm dedupe, e npx tempest doctor lista toda dependência duplicada.

    createQueryClient: o client fora do React

    O QueryProvider cria o client por dentro, e ali ele fica preso. Quando o app precisa dele fora do React — o queryClient.clear() no onSessionEnd da sessão, o persistQueryClientOffline({ queryClient }), um prefetch no loader da rota —, crie-o com createQueryClient() e entregue-o ao provider. É o mesmo client que o provider criaria, com os mesmos defaults:

    import { createQueryClient, createTempestAuth, QueryProvider } from "tempest-react-sdk";
import type { ReactNode } from "react";

export const queryClient = createQueryClient();

export const auth = createTempestAuth({
  baseURL: "https://api.example.com",
  onSessionEnd: () => {
    queryClient.clear();
  },
});

export function Providers({ children }: { children: ReactNode }) {
  return <QueryProvider client={queryClient}>{children}</QueryProvider>;
}
    • Aceita os mesmos overrides do provider: createQueryClient({ queries: { staleTime: STALE_TIME.LONG } }) mescla por chave, dentro de queries e de mutations, e mantém os defaults que você não nomeou.
    • Um client novo por chamada. Crie uma vez, no nível do módulo, e importe onde precisar.
    • Sem redigitar os defaults. Antes dele, o app que precisava do client copiava STALE_TIME.DEFAULT, CACHE_TIME.DEFAULT e shouldRetryQuery num new QueryClient({ … }), e a cópia divergia no dia em que um deles mudasse (#741). E o client sai da mesma cópia do @tanstack/react-query que o SDK usa, então não cai no "No QueryClient set" de cópia duplicada descrito acima.

    Query que lê só o IndexedDB: networkMode: "always"

    O TanStack Query pausa a query quando o navegador está offline: com o networkMode padrão ("online"), a queryFn nem roda. Para uma query que vai à rede, é o certo — ela espera o sinal voltar em vez de queimar uma requisição que vai falhar. Para uma query cuja queryFn lê só o IndexedDB, é um skeleton eterno. Medido offline (src/query/create-query-client.test.tsx):

    networkMode Chamadas da queryFn Estado
    "online" 0 pending / paused
    "offlineFirst" 1 success
    "always" 1 success

    Marque a query local, não o client inteiro:

    import { useQuery } from "@tanstack/react-query";

export function useDrafts(readDrafts: () => Promise<string[]>) {
  return useQuery({
    queryKey: ["drafts"],
    queryFn: readDrafts,
    networkMode: "always",
  });
}

    Por que não é o default do SDK

    defaultOptions={{ queries: { networkMode: "always" } }} funciona no QueryProvider e no createQueryClient desde sempre, mas vale para toda query: as que vão à rede passam a disparar offline e falhar, em vez de pausar até o sinal voltar. O SDK mantém o "online" e a query local diz que não depende de rede.

    Presets de tempo

    import { useQuery } from "@tanstack/react-query";
import { STALE_TIME, CACHE_TIME, REFETCH_TIME } from "tempest-react-sdk";

useQuery({
  queryKey: ["dashboard"],
  queryFn: fetchDashboard,
  staleTime: STALE_TIME.LONG, // 30 min — dado muda pouco
  gcTime: CACHE_TIME.LONG, // 1 h
  refetchInterval: REFETCH_TIME.FAST, // 30 s — polling de status
});
    • STALE_TIME: SHORT 30s, DEFAULT 5min, LONG 30min, INFINITE ∞
    • CACHE_TIME: SHORT 5min, DEFAULT 30min, LONG 1h
    • REFETCH_TIME: REALTIME 5s, FAST 30s, DEFAULT 60s, SLOW 5min

    Quando usar INFINITE

    STALE_TIME.INFINITE marca o dado como nunca obsoleto — o TanStack só refaz o fetch via invalidação manual. Ideal para listas estáticas (categorias, cidades) que mudam por deploy, não por uso.

    Query keys tipadas

    createQueryKeys recebe um scope (prefixo do domínio) e um mapa de builders. Cada saída já vem com o scope na frente, então a mesma key é montada de forma idêntica em toda a base de código:

    import { createQueryKeys } from "tempest-react-sdk";

export const userKeys = createQueryKeys("user", {
  me: () => ["me"] as const,
  byId: (id: string) => [id] as const,
  list: (filters: { page: number; size: number }) => ["list", filters] as const,
});

userKeys.all; // ["user"]
userKeys.me(); // ["user", "me"]
userKeys.byId("42"); // ["user", "42"]
userKeys.list({ page: 1, size: 20 }); // ["user", "list", { page: 1, size: 20 }]

    Note o all: ele é gerado automaticamente e é a key mais ampla do domínio — invalidá-lo derruba todas as queries user/* de uma vez.

    Exemplo completo — query + mutation + invalidação

    Esse componente lê o perfil com useQuery, atualiza com useMutation e invalida só as keys afetadas no sucesso:

    import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import { createApiClient, createQueryKeys } from "tempest-react-sdk";

interface User {
  id: string;
  name: string;
}

const api = createApiClient({ baseURL: import.meta.env.VITE_API_URL });

export const userKeys = createQueryKeys("user", {
  me: () => ["me"] as const,
  byId: (id: string) => [id] as const,
});

export function ProfileCard() {
  const queryClient = useQueryClient();

  const { data: user, isLoading } = useQuery({
    queryKey: userKeys.me(),
    queryFn: () => api.get<User>("/users/me"),
  });

  const rename = useMutation({
    mutationFn: (name: string) => api.patch<User>("/users/me", { body: { name } }),
    onSuccess: (updated) => {
      // Atualiza o cache local sem novo fetch...
      queryClient.setQueryData(userKeys.me(), updated);
      // ...e invalida o registro por id, caso outra tela o use.
      queryClient.invalidateQueries({ queryKey: userKeys.byId(updated.id) });
    },
  });

  if (isLoading) return <p>Carregando…</p>;

  return (
    <div>
      <h2>{user?.name}</h2>
      <button disabled={rename.isPending} onClick={() => rename.mutate("Novo nome")}>
        Renomear
      </button>
    </div>
  );
}

    Por que setQueryData + invalidateQueries?

    setQueryData aplica a resposta da mutation no cache imediatamente (UI sem flicker), enquanto invalidateQueries marca queries relacionadas como obsoletas pra revalidar no background. Usar uma key factory garante que a key invalidada seja exatamente a mesma que a query consultou.

    Padrão de organização: cada domínio em src/constants/query-keys/<dominio>.ts, agrupados num barrel.

    useOfflineMutation

    Quando o app é offline-first, uma mutation não deve bater na rede direto — ela grava no outbox do createOfflineSync e sincroniza depois. useOfflineMutation faz a ponte entre o motor de sync e o TanStack Query: no mutate ele enfileira a entrada, atualiza o cache da query otimisticamente, dá o flush e faz rollback do cache se o enqueue falhar.

    import { useOfflineMutation } from "tempest-react-sdk";
import { notesSync } from "@/sync/engine";
import type { Note } from "@/sync/types";

function useAddNote() {
  return useOfflineMutation<Note, Note[], Note>({
    sync: notesSync,
    queryKey: ["notes"],
    toEntry: (note) => ({ op: "create", recordId: note.id, payload: note }),
    applyOptimistic: (current = [], note) => [...current, note],
  });
}

// const addNote = useAddNote();
// addNote.mutate({ id: crypto.randomUUID(), text: "offline!" });
    • toEntry mapeia as variáveis pra { op, recordId, payload } do outbox.
    • applyOptimistic produz o próximo valor do cache; o anterior é restaurado se o enqueue lançar.
    • flush (default true → "after-mutation") dispara a sincronização; false deixa isso pro useOfflineSync.
    • invalidate (default false) revalida a queryKey no onSettled.

    Helpers de cache de lista

    Para o caso comum (cache é uma lista), use upsertById() / removeById() no lugar de escrever o spread na mão:

    import { upsertById, removeById } from "tempest-react-sdk";

applyOptimistic: upsertById(); // insere ou faz merge por `id`
applyOptimistic: removeById(); // remove por `id` (op "delete")
// campo custom: upsertById("uuid")

    A entrega ao servidor acontece no flush

    O mutate resolve com o id da entrada no outbox, não com a resposta do servidor — a entrega real roda no loop de flush do motor, então a UI atualiza na hora e sobrevive a reloads e a períodos offline.

    persistQueryClientOffline

    Persiste o cache do QueryClient no IndexedDB e restaura no boot — um reload ou início offline mostra os últimos dados conhecidos em vez de telas vazias. Self-contained: usa dehydrate/hydrate do próprio @tanstack/react-query, sem precisar do @tanstack/react-query-persist-client.

    import { persistQueryClientOffline } from "tempest-react-sdk";
import { queryClient } from "@/lib/query";

const persistence = persistQueryClientOffline({ queryClient });
await persistence.restore(); // antes do primeiro render

export async function logout(): Promise<void> {
    await persistence.clear({ resetClient: true });
}

// no teardown:
persistence.unsubscribe();

    As gravações são throttled (throttleMs, default 1s) e assinam o cache. flush() grava na hora; unsubscribe() para de persistir; clear() encerra a sessão persistida.

    Logout: clear() é terminal

    clear() cancela a gravação pendente, para de ouvir o cache, espera a gravação que já estiver em voo e só então apaga o snapshot. Depois dele, restore() e flush() desse handle não fazem nada. É isso que impede o cache do usuário anterior de voltar: antes da 0.77.0, clear() só apagava a linha, e tanto a gravação pendente na última janela de throttle quanto o primeiro evento de cache depois do logout (a primeira query do próximo usuário) regravavam as respostas autenticadas de quem saiu — que o restore() do próximo boot hidratava para quem estivesse no navegador.

    • Chame persistence.clear() no seu fluxo de logout (ou no hook de fim de sessão do seu auth). É idempotente e pode ser chamado mais de uma vez, inclusive em paralelo.
    • clear({ resetClient: true }) é o logout em uma chamada: depois de parar a persistência e apagar o snapshot, ele também faz queryClient.clear(), então nada do usuário anterior fica nem no disco nem em memória.
    • Sem a opção (default false), o QueryClient em memória não é tocado — ele é do app, que pode querer manter queries públicas (um catálogo, feature flags) e tirar só as keys do usuário com removeQueries. Como a persistência já parou, a ordem entre persistence.clear() e a sua limpeza manual não importa. Com auth, o client que sobra ainda guarda respostas da sessão que acabou, então ele fica marcado como encerrado: nenhum handle sobre ele grava — o novo do login, nem o de outra key — até o client ser zerado (veja abaixo).
    • Para persistir a próxima sessão, crie um handle novo no login: o handle antigo não volta a gravar. Em build de dev, o primeiro restore(), flush() ou query nova num handle encerrado gera um console.warn avisando disso.
    • Handles de sessões diferentes não se atropelam. Enquanto um clear() está rodando, o restore() e as gravações de um handle novo com o mesmo databaseName + key esperam ele terminar — mesmo que o logout não tenha sido aguardado.
    • Se a remoção no IndexedDB falhar, resetClient limpa o QueryClient mesmo assim, e o erro chega a quem chamou.
    • Sessão que acaba sem clear() (token vencido, crash, aba fechada logada) não passa pelo logout. Para ela, passe getPrincipal: () => userId: cada gravação carimba o snapshot com a impressão de quem está logado, e o restore() só hidrata o snapshot do mesmo dono. O de outra pessoa é ignorado, não apagado — app com cookie que só descobre o usuário depois do /me não perde o próprio cache —, e a próxima gravação o substitui. Snapshot gravado antes da opção não tem carimbo e não é restaurado: custa um boot frio, uma vez.
    • O handle fica preso ao primeiro dono logado que ele vê — numa mudança do cache, numa gravação ou num restore. É a mudança do cache que fixa o dono do dado: a gravação tem throttle, e sem isso uma sessão que vencia (ou outra conta que entrava) dentro da primeira janela recebia as respostas de quem saiu, carimbadas como anônimas ou como suas (#580). Depois disso, uma gravação com outro dono — ninguém, porque o token venceu sem clear(), ou outra conta entrando na mesma aba — apaga o snapshot em vez de carimbar as respostas de quem saiu com o dono novo (#563); se o mesmo usuário voltar, o handle volta a gravar. Gravação antes de alguém logar continua anônima e é restaurada enquanto ninguém estiver logado, então app que persiste dado de visitante segue igual. Snapshot anônimo gravado pela 0.82.0 não é restaurado (pode conter o cache de uma sessão vencida): um boot frio, uma vez. Para a próxima sessão persistir, encerre o handle com clear({ resetClient: true }) e crie um novo no login: o QueryClient em memória ainda guarda as respostas de quem saiu, e um handle novo sobre ele as carimbaria com o dono novo. Com auth, a biblioteca não zera o client por você, mas garante que um handle novo sobre um client que ainda guarda uma sessão encerrada apaga em vez de gravar até o client ser zerado (veja abaixo); só com getPrincipal, limpar o client é com o app.
    • Principal ainda desconhecido: isPrincipalKnown. Para o getPrincipal, null e undefined querem dizer ninguém logado — o mesmo contrato do resto do SDK, então () => user?.id continua valendo. "Ainda não sei" é outro estado: app com sessão por cookie só descobre o usuário depois do /me, e uma gravação que rodava antes disso carimbava as respostas de A como anônimas; se a aba fechasse antes da próxima gravação, o boot deslogado seguinte as hidratava (#590). Passe isPrincipalKnown: () => false até a resposta do /me chegar, seja ela qual for. Enquanto for false, nada é gravado (a gravação é reagendada para a próxima janela), mudança no cache não prende o dono e o restore() não hidrata nada — chame-o de novo quando o principal for conhecido. Um isPrincipalKnown que lança conta como desconhecido. Sem getPrincipal, a opção é ignorada.
    • Handle que hidratou snapshot anônimo não o recarimba quando alguém loga nele: a linha anônima pode ser de uma conta cujo principal ainda não era conhecido na gravação, e recarimbá-la entregava as respostas de A a B (#590). A gravação apaga a linha, como na troca de conta (#563), e em build de dev sai um console.warn. App de visitante que depois faz login perde a persistência daquela sessão; para continuar persistindo, chame clear({ resetClient: true }) nele e crie um handle novo — sem zerar o client, o handle novo carimbaria a linha anônima hidratada com a conta que entrou.
    import { persistQueryClientOffline } from "tempest-react-sdk";
import { QueryClient } from "@tanstack/react-query";

const queryClient = new QueryClient();
let me: { id: string } | null = null;
let meResolved = false;

const persistence = persistQueryClientOffline({
    queryClient,
    getPrincipal: () => me?.id,
    isPrincipalKnown: () => meResolved,
});

export async function boot(): Promise<void> {
    const response = await fetch("/api/me", { credentials: "include" });
    me = response.ok ? ((await response.json()) as { id: string }) : null;
    meResolved = true;
    await persistence.restore();
}

    Com createTempestAuth: passe auth

    App com createTempestAuth não precisa montar getPrincipal nem isPrincipalKnown à mão: passe o próprio preset em auth (#596).

    import { createTempestAuth, persistQueryClientOffline } from "tempest-react-sdk";
import { QueryClient } from "@tanstack/react-query";

interface User {
    id: string;
}

const auth = createTempestAuth<User>({
    baseURL: "https://api.example.com",
    withCredentials: true,
    logoutPath: "/api/auth/logout",
    mePath: "/api/auth/me",
});
const queryClient = new QueryClient();
const persistence = persistQueryClientOffline({ queryClient, auth });

export async function boot(): Promise<void> {
    await auth.refresh().catch(() => undefined);
    await persistence.restore();
}
    • O dono do cache é a sessão: o principal é auth.sessionKey(), que sobrevive ao reload e à rotação do token e muda a cada login. Login novo da mesma conta começa com o cache frio — é um cache, e nenhuma conta herda o de outra.
    • "Ainda não sei" vem do preset: auth.isSessionKnown() é false enquanto um login(), um restore() ou uma troca de conta está em voo, e enquanto o refresh() do boot ainda restaura a sessão do cookie. Nesse intervalo nada é gravado, nada prende o dono e o restore() não hidrata nada. Uma sessionKey() que lança também conta como desconhecida.
    • Toda sessão instalada enquanto o cache vive conta, não só a que uma mudança do cache viu. O preset avisa cada instalação, e o handle anota a sessão no QueryClient. Quando uma segunda sessão, ou ninguém depois de uma, foi instalada — logout() em outra aba, logout() nesta sem clear(), outro login() por cima —, toda gravação apaga a linha e o restore() não hidrata nada, porque o cache pode ter respostas da sessão que acabou. Inclui a requisição que saiu sem token e que o api client repetiu com o token de um login() ou do refresh() do boot em voo: se essa sessão acabou antes da resposta chegar, ninguém estava logado nem na saída nem na chegada, e, antes desta correção, a resposta de A era carimbada p:anonymous para o próximo boot deslogado (auditoria run-12, C1). Ninguém seguido de uma sessão não conta como fim (o dado de visitante não é de conta nenhuma), e a rotação do token mantém a chave.
    • A anotação é do QueryClient, não do handle. Um handle novo sobre o mesmo client continua apagando até o client ser zerado, e só duas coisas zeram: clear({ resetClient: true }) do handle anterior (a anotação sai depois do queryClient.clear(), quando nada da sessão encerrada fica em memória — desde que ninguém esteja logado nessa hora) ou um handle criado com o client vazio (queryClient.clear() ou removeQueries() de tudo antes). O clear() sem resetClient não zera: o client ainda guarda as respostas da sessão, então a anotação fica marcada como encerrada, e isso vale também para o handle de outra key sobre o mesmo client. Antes da 0.85.0, esse clear() apagava a anotação, e o handle novo criado no login carimbava as respostas de A com a impressão de B — e o restore() do próximo boot de B as hidratava (auditoria run-13, C1). Sem isso, seguir o conselho "crie um handle novo depois do login" carimbava as respostas de A, ainda em memória, como de B. O custo é deliberado: depois de uma sessão que acaba sem clear() — inclusive a sessão salva que venceu no boot —, a próxima não persiste naquele carregamento até o client ser zerado ou a página recarregar. Para não pagar, chame clear({ resetClient: true }) no fim de toda sessão e crie o handle de novo.
    • O reset vai no onSessionEnd ou depois do logout(), não antes. Um clear({ resetClient: true }) com a sessão de A ainda instalada não apaga a anotação: o handle encerrado já não observa a sessão, e uma query de A que caísse no intervalo (refetch, intervalo, foco, prefetch) chegava ao handle de B como dado anônimo e era gravada com a impressão de B — o próximo boot de B hidratava as respostas de A (auditoria run-14, C1, #609). Agora a anotação fica marcada como encerrada até um handle ser criado com o client vazio; se nada de A entrou no intervalo, o handle do login de B persiste normalmente.
    • A resposta de uma sessão que acabou não chega ao cache. O auth.api recusa, com SessionSupersededError, a resposta de uma request que saiu com o token de uma sessão encerrada antes de ela chegar — inclusive a mutation iniciada antes do logout(), cujo onSuccess fazia setQueryData com os dados de A já na sessão de B (na tela e no snapshot). Veja Auth → Refresh em voo e troca de conta. Um fetch seu, fora do auth.api, continua sendo responsabilidade do app.
    • O setQueryData feito deslogado depois de uma sessão não vai para o snapshot (#653). Uma promise do app iniciada na sessão de A — um onSuccess que faz await de algo seu e depois setQueryData — pode gravar dados de A depois do logout() e do clear({ resetClient: true }), quando nenhum handle observa o client: o de A já acabou, o de B ainda não existe. Antes, o handle criado no login de B começava uma anotação nova sobre esse client e gravava os dados de A com a impressão de B (medido na 0.90.0: a linha saía com o dono de B e a-late: ["private-of-A"]; com o handle novo criado logo após o logout, o snapshot anônimo do intervalo já os levava). Agora o client inteiro é observado desde o primeiro handle com auth ou getPrincipal, e a query escrita por setQueryData com ninguém logado, depois que alguém esteve, fica fora de todo snapshot até um fetch substituir o dado. Só ela: o resto do cache e a persistência de B continuam. Uma query buscada (fetch) no intervalo — o catálogo público da tela de login — é gravada normalmente, e o setQueryData de visitante antes de qualquer login na aba também. O custo: um setQueryData legítimo de visitante depois de um logout (carrinho anônimo, rascunho público) não persiste até a query ser buscada de novo; na tela e em memória nada muda. Reproduzido em src/query/offline-persistence.signed-out-write.test.ts (npx vitest run src/query/offline-persistence.signed-out-write.test.ts).
    • O que fica de fora: com um objeto de sessão seu em auth (não o preset), não há aviso de instalação — a sessão só é lida em mudança de cache, gravação e restore, e uma sessão instalada e encerrada entre duas delas passa despercebida. O handle só anota as sessões enquanto as observa: depois de unsubscribe(), o flush() não grava nada, e um handle criado sobre um client que já guarda respostas não tem como saber de qual sessão elas vieram — crie o handle no boot, antes da primeira query. E um backend que autentica por cookie sem bearer (withCredentials) não instala sessão nenhuma no SDK: o que ele responde é gravado como anônimo, como em qualquer app sem login.
    • Quer o id do usuário como dono? Passe getPrincipal junto com auth. Aí o principal também precisa estar carregado: com sessão instalada e getPrincipal respondendo ninguém (o perfil ainda não veio), conta como desconhecido — não como anônimo.
    • Chame o restore() depois do refresh() do boot. Antes dele, a sessão ainda não existe, e o restore() só hidrata o que é de ninguém.

    Antes, a única proteção era a frase do item isPrincipalKnown acima: sem ela, a aba fechada antes do /me deixava as respostas de A carimbadas como anônimas, e o próximo boot deslogado as hidratava. Reproduzido em src/query/offline-persistence.auth.test.ts (npx vitest run src/query/offline-persistence.auth.test.ts); as sessões instaladas no meio da requisição e o handle novo sobre o mesmo client, em src/query/offline-persistence.lifetime.test.ts.

    Mudou na 0.77.0: o handle morre no clear()

    Antes, o mesmo handle continuava gravando depois do clear(). Se o seu app guarda a persistence no nível do módulo e reaproveita depois do login, ele para de persistir a partir da 0.77.0. Crie o handle dentro da sessão:

    import { persistQueryClientOffline, type OfflineQueryPersistence } from "tempest-react-sdk";
import { QueryClient } from "@tanstack/react-query";

const queryClient = new QueryClient();
let persistence: OfflineQueryPersistence | null = null;

export async function startSession(): Promise<void> {
    persistence = persistQueryClientOffline({ queryClient });
    await persistence.restore();
}

export async function endSession(): Promise<void> {
    await persistence?.clear({ resetClient: true });
    persistence = null;
}

    Chame startSession() no boot com usuário logado e depois de cada login; endSession() no logout.

    Recap

    • <QueryProvider> na raiz — um por app — entrega defaults calibrados; sobrescreva via defaultOptions ou client.
    • createQueryClient() dá o mesmo client com os mesmos defaults, para usar fora do React (clear() no fim da sessão, persistência, prefetch).
    • Query que lê só o IndexedDB leva networkMode: "always"; as que vão à rede continuam pausando offline.
    • STALE_TIME / CACHE_TIME / REFETCH_TIME substituem números mágicos por presets nomeados.
    • createQueryKeys(scope, builders) gera keys tipadas e consistentes, com um all automático pra invalidação ampla.
    • Combine setQueryData (resposta imediata) com invalidateQueries (revalidação) usando a mesma key factory.
    • useOfflineMutation liga o motor offline ao cache: enqueue + optimistic update + flush + rollback.
