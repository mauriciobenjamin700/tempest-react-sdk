    App de campo offline

    O técnico da cooperativa sai às 6h da cidade, roda 80 km de estrada de chão e passa o dia de fazenda em fazenda. Em cada porteira ele faz a mesma vistoria: quantas cabeças tem o rebanho, se os bebedouros estão limpos, se a cerca aguenta, se a vacinação está em dia. Tira fotos. Anota o que o produtor falou.

    No pasto não tem sinal. Às vezes pega um 2G fraco perto da sede, que cai no meio do envio. O sinal de verdade só volta à noite, no hotel da cidade.

    Esta receita monta o app que esse técnico usa: um PWA que funciona inteiro sem rede, guarda tudo no aparelho e envia sozinho quando o sinal aparece — inclusive as fotos, que retomam de onde pararam quando a conexão cai no meio. 🚜

    Esta receita é sobre o campo

    O motor de sincronização em si (outbox, watermark, pull paginado) está explicado peça por peça em Offline Sync (FastAPI). Aqui você vê esse motor trabalhando num app real, junto de câmera, GPS, upload resumível e exportação.

    O que vamos construir

    • Lista de visitas — lê do aparelho, nunca da rede. Mostra o que já foi enviado, o que está esperando sinal e o que deu conflito.
    • Formulário de vistoria — fazenda, produtor (com CPF validado), rebanho, checklist, observações e a localização GPS, que funciona sem internet.
    • Fotos da câmera — reduzidas e comprimidas no próprio aparelho antes de ocupar espaço, e enviadas por upload resumível quando houver sinal.
    • Status de sincronização — o badge no topo, o painel "envio pendente" e a barra de offline.
    • Conflito — o supervisor aprovou a visita no escritório enquanto o técnico ainda editava no pasto. O app mostra isso e deixa ele escolher.
    • Exportar a visita — planilha .xlsx + fotos num .zip, gerados sem rede, para o técnico mandar ao produtor pelo WhatsApp.
    • PWA — abre sem rede, pede armazenamento persistente e não troca de versão no meio de uma vistoria.

    E os estados que toda tela real tem: carregando, vazio, erro, sucesso — e a tela de celular, que aqui é a única que importa.

    O contrato com o backend

    O backend é um FastAPI em cima do tempest-fastapi-sdk, seguindo a receita de offline-sync dele. O app conversa com quatro rotas, todas sob o root_path="/api":

    Rota O que faz
    PUT /api/visits/{id} Upsert idempotente da visita. O id é gerado no aparelho.
    GET /api/visits/changes?since&cursor&limit Delta paginado desde o último server_time.
    GET /api/visits/{id} A versão do servidor, usada para resolver conflito.
    POST /api/uploads (tus) Upload resumível das fotos.

    Servidor tus no backend

    A rota /api/uploads precisa de um servidor tus. A partir da 0.370.0, o tempest-fastapi-sdk tem um pronto (make_tus_router), que amarra cada upload ao dono via current_user_id — o que importa num tablet compartilhado. Em backend sem ele, tusd atrás do mesmo proxy é o caminho comum. A tabela do que o servidor precisa responder está em Upload resumível.

    O código, arquivo por arquivo

    1. O modelo

    // src/visits/types.ts
export type VisitStatus = "draft" | "done" | "approved";

export type VisitSyncState = "pending" | "synced" | "conflict";

export interface VisitChecklist {
  water: boolean;
  fences: boolean;
  vaccination: boolean;
  pasture: boolean;
}

export interface Visit {
  id: string;
  technician_id: string;
  farm_name: string;
  producer_name: string;
  producer_cpf: string;
  herd_size: number;
  checklist: VisitChecklist;
  notes: string;
  status: VisitStatus;
  latitude: number | null;
  longitude: number | null;
  visited_at: string;
  updated_at: string;
  sync_state: VisitSyncState;
  conflict_detail: string | null;
}

export interface VisitPhoto {
  id: string;
  visit_id: string;
  technician_id: string;
  blob: Blob | null;
  thumb: Blob;
  bytes: number;
  taken_at: string;
  upload_url: string | null;
}

export interface PhotoRef {
  id: string;
  url: string;
  taken_at: string;
}

export interface VisitDto extends Omit<Visit, "sync_state" | "conflict_detail"> {
  photos: PhotoRef[];
  is_deleted: boolean;
}

export type VisitPayload = Omit<VisitDto, "is_deleted">;

export interface VisitChangesPage {
  items: VisitDto[];
  next_cursor: string | null;
  has_more: boolean;
  limit: number;
  server_time: string;
}

export function fromDto(dto: VisitDto): Visit {
  return {
    id: dto.id,
    technician_id: dto.technician_id,
    farm_name: dto.farm_name,
    producer_name: dto.producer_name,
    producer_cpf: dto.producer_cpf,
    herd_size: dto.herd_size,
    checklist: dto.checklist,
    notes: dto.notes,
    status: dto.status,
    latitude: dto.latitude,
    longitude: dto.longitude,
    visited_at: dto.visited_at,
    updated_at: dto.updated_at,
    sync_state: "synced",
    conflict_detail: null,
  };
}

export function toPayload(visit: Visit, photos: PhotoRef[]): VisitPayload {
  return {
    id: visit.id,
    technician_id: visit.technician_id,
    farm_name: visit.farm_name,
    producer_name: visit.producer_name,
    producer_cpf: visit.producer_cpf,
    herd_size: visit.herd_size,
    checklist: visit.checklist,
    notes: visit.notes,
    status: visit.status,
    latitude: visit.latitude,
    longitude: visit.longitude,
    visited_at: visit.visited_at,
    updated_at: visit.updated_at,
    photos,
  };
}

    Três coisas para notar:

    • O id nasce no aparelho (crypto.randomUUID()). É ele que torna o PUT um upsert seguro: mandar a mesma visita duas vezes não cria duas.
    • sync_state e conflict_detail são só locais — o servidor nunca os vê. Eles dizem à tela se a visita está esperando sinal, já foi, ou bateu num conflito.
    • A foto guarda o Blob em si, não uma URL. No pasto não tem servidor para apontar. Depois que ela sobe, o blob vira null e fica só a miniatura (thumb): o aparelho não guarda o que o servidor já tem.

    2. A sessão

    // src/lib/auth.ts
import { createTempestAuth, requestPersistentStorage } from "tempest-react-sdk";

export interface Technician {
  id: string;
  name: string;
  email: string;
}

export const auth = createTempestAuth<Technician>({
  baseURL: import.meta.env.VITE_API_URL,
  prefix: "/api",
  mePath: "/auth/me",
});

export function currentTechnicianId(): string | null {
  return auth.useAuthStore.getState().user?.id ?? null;
}

export async function signIn(email: string, password: string): Promise<void> {
  await auth.login({ email, password });
  void requestPersistentStorage();
}

    O createTempestAuth monta login, refresh e o auth.api já autenticado. O currentTechnicianId é lido fora do React — pelo motor de sync e pelo banco — por isso é uma função, não um hook.

    O signIn pede armazenamento persistente logo depois do login. Sem ele, o navegador pode apagar o IndexedDB sob pressão de disco — e no Safari fora da tela inicial, depois de ~7 dias sem uso. O pedido fica aqui, e não no motor de sync, porque no Firefox ele abre um pedido de permissão: no login o técnico entende por que o app pergunta; no meio de um envio em segundo plano, não.

    3. O banco no aparelho

    // src/visits/db.ts
import { createOfflineDatabase } from "tempest-react-sdk";
import type { Visit, VisitPhoto } from "@/visits/types";

const database = createOfflineDatabase<{ visits: Visit; photos: VisitPhoto }>({
  databaseName: "CampoVisitas",
  version: 1,
  tables: {
    visits: {
      indexes: "&id, technician_id, visited_at, sync_state",
      ownerField: "technician_id",
    },
    photos: {
      indexes: "&id, visit_id, technician_id",
      ownerField: "technician_id",
    },
  },
});

export const visits = database.store<Visit>("visits");
export const photos = database.store<VisitPhoto>("photos");

    Visitas e fotos moram na mesma base, com o createOfflineDatabase. Elas pertencem uma à outra: você lê, apaga e migra as duas juntas.

    O ownerField: "technician_id" faz cada put/list respeitar o dono. Quando dois técnicos dividem o mesmo tablet da cooperativa, um não vê as visitas do outro.

    Subiu um índice? Suba a version

    Mudar indexes sem subir version quebra a abertura do banco. Detalhes em Offline › Migrations.

    4. O motor de sync — com as fotos dentro

    Este é o coração do app.

    // src/visits/sync.ts
import { createOfflineSync, encodeIdSegment, isApiError, lastWriteWins } from "tempest-react-sdk";
import { auth, currentTechnicianId } from "@/lib/auth";
import { photos, visits } from "@/visits/db";
import { listPhotos } from "@/visits/photos";
import {
  fromDto,
  toPayload,
  type PhotoRef,
  type Visit,
  type VisitChangesPage,
  type VisitDto,
} from "@/visits/types";

const PHOTO_CHUNK_SIZE = 256 * 1024;

export const visitSync = createOfflineSync<Visit, VisitDto>({
  databaseName: "CampoVisitasOutbox",
  watermark: { storageKey: "campo.visits.watermark" },
  getPrincipal: currentTechnicianId,
  foreignEntries: "hold",
  coalesce: true,

  attachments: {
    list: async (entry) =>
      (await listPhotos(entry.recordId)).map((photo) => ({
        id: photo.id,
        blob: photo.blob,
        uploadedUrl: photo.upload_url,
      })),
    upload: (photo) => ({
      endpoint: auth.api.url("/uploads"),
      chunkSize: PHOTO_CHUNK_SIZE,
      metadata: { photo_id: photo.id, filetype: photo.blob.type },
      getToken: auth.getToken,
    }),
    onUploaded: async (photo, url) => {
      await photos.update(photo.id, { upload_url: url, blob: null });
    },
  },

  deliver: async (entry) => {
    const visit = entry.payload;
    if (visit === undefined) return;

    const takenAt = new Map(
      (await listPhotos(entry.recordId)).map((photo) => [photo.id, photo.taken_at]),
    );
    const photoRefs: PhotoRef[] = (entry.attachments ?? []).map((ref) => ({
      ...ref,
      taken_at: takenAt.get(ref.id) ?? visit.visited_at,
    }));

    try {
      await auth.api.put(`/visits/${encodeIdSegment(entry.recordId)}`, {
        body: toPayload(visit, photoRefs),
      });
    } catch (error) {
      if (isApiError(error) && error.status === 409 && error.code === "VISIT_LOCKED") {
        await visits.update(entry.recordId, {
          sync_state: "conflict",
          conflict_detail: error.detail,
        });
        return;
      }
      throw error;
    }

    const local = await visits.get(entry.recordId);
    if (local?.updated_at === visit.updated_at) {
      await visits.update(entry.recordId, { sync_state: "synced" });
    }
  },

  pullPage: async (since, cursor) => {
    const page = await auth.api.get<VisitChangesPage>("/visits/changes", {
      params: { since: since ?? undefined, cursor: cursor ?? undefined, limit: 100 },
    });
    return {
      items: page.items,
      nextCursor: page.has_more ? page.next_cursor : null,
      serverTime: page.server_time,
    };
  },

  applyRemote: async (dto) => {
    const owner = currentTechnicianId();
    if (owner === null) return;

    const local = await visits.get(dto.id);
    if (dto.is_deleted) {
      if (local?.sync_state !== "pending") await visits.delete(dto.id);
      return;
    }

    const remote = fromDto(dto);
    if (local?.sync_state === "pending") {
      const winner = lastWriteWins(local, remote, (visit) => visit.updated_at);
      if (winner === local) return;
    }
    await visits.put(remote, owner);
  },
});

export async function saveVisit(visit: Visit): Promise<void> {
  const owner = currentTechnicianId();
  if (owner === null) throw new Error("Sua sessão expirou. Entre de novo para salvar.");

  const existing = await visits.get(visit.id);
  const record: Visit = {
    ...visit,
    technician_id: owner,
    updated_at: new Date().toISOString(),
    sync_state: "pending",
    conflict_detail: null,
  };

  await visits.put(record, owner);
  await visitSync.enqueue(existing === undefined ? "create" : "update", record.id, record);
  void visitSync.flush("after-mutation");
}

export async function acceptServerVersion(visitId: string): Promise<void> {
  const owner = currentTechnicianId();
  if (owner === null) return;

  const dto = await auth.api.get<VisitDto>(`/visits/${encodeIdSegment(visitId)}`);
  await visits.put(fromDto(dto), owner);
}

    Vamos por partes. 🔍

    saveVisit: o aparelho primeiro, a rede depois

    saveVisit grava no IndexedDB, coloca a visita na outbox e pede um flush. Nenhuma dessas três coisas precisa de rede. Sem sinal, o flush é pulado sozinho (summary.skipped) e a entrada fica esperando — a tela já respondeu.

    O create/update é só rótulo: como a rota é upsert, os dois viram o mesmo PUT.

    E o coalesce: true junta as edições: o técnico que salva a mesma visita dez vezes sem sinal manda um PUT quando a rede volta, com a versão mais nova — não dez. As fotos sobem uma vez só de qualquer jeito (quem já tem upload_url não sobe de novo), mas sem a opção cada PUT intermediário ainda gastava um round-trip num sinal que mal se sustenta. Detalhes, e o que não se junta, em Dez edições, um request.

    attachments: as fotos sobem antes da visita

    As fotos são anexos da visita. Com a opção attachments, o createOfflineSync faz, para cada entrada, nesta ordem:

    1. Pergunta ao list quais fotos a visita tem. Elas moram no store do app — a outbox não guarda cópia do arquivo.
    2. Sobe as que ainda não têm upload_url, uma por uma, com o createResumableUpload e as opções que o upload devolve.
    3. Chama o onUploaded de cada uma, que grava a URL e troca o blob por null: a foto já está no servidor, e o aparelho fica só com a miniatura.
    4. Chama o deliver com as URLs em entry.attachments, e ele manda o PUT da visita.

    Por que as fotos não vão numa entrada própria da outbox? Porque cada foto seria outro registro, e o motor só ordena entradas do mesmo registro — um registro que falha não segura os outros. A foto falharia no 2G, e o PUT da visita chegaria ao servidor apontando para uma foto que não existe. Como anexo, elas herdam tudo que o motor já faz:

    • Se qualquer coisa falha — a foto 3 de 5, ou o PUT —, a entrada continua na fila com attempts incrementado, e o próximo flush tenta de novo. Com a foto falhando, o deliver nem é chamado.
    • As fotos 1 e 2 já ganharam upload_url e não sobem de novo.
    • A foto 3 retoma do byte em que parou: a key padrão é outbox-attachment:<id>, a mesma em todo flush, então o upload resumível acha o registro dele e continua com um HEAD + PATCH.
    • A ordem por registro é preservada: uma visita que falhou não deixa a edição seguinte dela passar na frente. Outras visitas seguem normalmente.
    • Visita segurada para outro técnico (foreignEntries: "hold") não sobe foto nenhuma.

    O deliver só junta o taken_at de cada foto às URLs, para o corpo que o backend espera.

    Por que a key leva o id da foto

    A impressão digital padrão do upload resumível usa nome e lastModified do File. Um Blob vindo do IndexedDB não tem nenhum dos dois, então dois blobs do mesmo tamanho colidiriam. Por isso o motor usa outbox-attachment:<id> como key padrão: cada foto tem o seu ponto de retomada. Veja Retomar depois de um reload.

    Chunk pequeno para sinal ruim

    O padrão do upload resumível é DEFAULT_CHUNK_SIZE (5 MiB), maior que uma foto inteira comprimida. Com chunkSize: 256 * 1024, uma queda de sinal perde no máximo um pedaço pequeno. O custo é mais round-trips — que é o que você quer trocar num 2G que cai.

    O getToken: auth.getToken não é por acaso: com o getter do próprio createTempestAuth, o ponto de retomada fica preso à sessão. Se outro técnico entrar no tablet, ele não retoma o upload do anterior. Detalhes em getToken: auth.getToken.

    getPrincipal: o tablet compartilhado

    Com getPrincipal, cada entrada da outbox ganha a impressão de quem a criou. Antes de cada envio o motor confere de novo:

    Quem está logado no envio O que acontece
    o mesmo técnico entregue
    ninguém fica na fila até ele voltar
    outro técnico fica na fila, sem envio, até o dono voltar

    A terceira linha é o foreignEntries: "hold". Ela protege o servidor de receber a vistoria do Carlos com o token da Ana e protege o trabalho do Carlos: se ele sair com visitas pendentes e a Ana entrar e sincronizar, as visitas dele continuam no tablet e saem quando ele entrar de novo. O padrão do motor ("drop") as apagaria — serve ao aparelho pessoal, não ao tablet da cooperativa. Detalhes em Offline Sync › Aparelho compartilhado.

    Uma visita do Carlos que a Ana editar espera a edição dele sair primeiro: a ordem por registro vale também para entrada segurada.

    pullPage e applyRemote: o que vem do escritório

    O pull traz o que mudou no servidor desde o último server_time. O pullPage só traduz o formato: has_more vira nextCursor: null quando a página acabou.

    O applyRemote decide o conflito, e a regra é simples:

    • Visita local já enviada (synced ou conflict)? A do servidor substitui.
    • Visita local pendente? Vence a mais recente por updated_at, com o lastWriteWins. Se a local for mais nova, ela fica, e o próximo flush a envia.
    • Tombstone (is_deleted)? Apaga — a não ser que exista edição local pendente.

    O 409 VISIT_LOCKED: conflito que a máquina não resolve

    O supervisor aprovou a visita no escritório. O técnico, sem sinal, ainda corrigiu o número de cabeças. Quando o PUT chega, o servidor recusa com 409 VISIT_LOCKED.

    Retentar não adianta — a quinta tentativa recebe a mesma resposta. Então o deliver não lança: marca a visita local como conflict, guarda a frase do servidor e resolve. A entrada sai da fila, e a decisão vai para quem sabe decidir: o técnico, na tela. O acceptServerVersion busca a versão do escritório e a grava por cima.

    Variante: conflito por version em vez de relógio

    updated_at vem do relógio do aparelho. Tablet com data errada (bateria que zerou, fuso trocado) faz uma edição antiga parecer nova. Se o seu backend mantém um contador version que ele mesmo incrementa a cada escrita, extraia a regra para um pickWinner e troque a comparação:

    // src/visits/conflict.ts
import { lastWriteWins } from "tempest-react-sdk";
import type { Visit } from "@/visits/types";

export function pickWinner(local: Visit, remote: Visit): Visit {
  return lastWriteWins(local, remote, (visit) => visit.updated_at);
}

import { higherVersionWins } from "tempest-react-sdk";

export interface VersionedVisit {
  id: string;
  version: number;
}

export function pickWinner<T extends VersionedVisit>(local: T, remote: T): T {

    No applyRemote, troque o lastWriteWins(...) por pickWinner(local, remote). Nos dois, empate vai para o servidor.

    5. As fotos no aparelho

    // src/visits/photos.ts
import type { CompressedImage, ProcessedImage } from "tempest-react-sdk/imaging";
import { currentTechnicianId } from "@/lib/auth";
import { photos } from "@/visits/db";
import type { VisitPhoto } from "@/visits/types";

export async function addPhoto(
  visitId: string,
  image: CompressedImage,
  thumb: ProcessedImage,
): Promise<VisitPhoto> {
  const owner = currentTechnicianId();
  if (owner === null) throw new Error("Sua sessão expirou. Entre de novo para fotografar.");

  const photo: VisitPhoto = {
    id: crypto.randomUUID(),
    visit_id: visitId,
    technician_id: owner,
    blob: image.blob,
    thumb: thumb.blob,
    bytes: image.bytes,
    taken_at: new Date().toISOString(),
    upload_url: null,
  };
  await photos.put(photo, owner);
  return photo;
}

export function listPhotos(visitId: string): Promise<VisitPhoto[]> {
  const owner = currentTechnicianId();
  if (owner === null) throw new Error("Sua sessão expirou. Entre de novo para ver as fotos.");
  return photos.listBy("visit_id", visitId, owner, { orderBy: "taken_at" });
}

    O listBy vai pelo índice visit_id e continua preso ao dono: o photos.raw.where("visit_id") direto no Dexie também usava o índice, mas devolvia a foto de outro técnico com a mesma visita. Sem ninguém logado, a função lança em vez de chamar listBy sem dono — que listaria as fotos de todos.

    A foto entra no banco com upload_url: null. Quem a manda para o servidor é o motor de sync, antes do deliver, na próxima vez que a visita sincronizar.

    6. As queries da tela

    // src/visits/use-visits.ts
import { useQuery, type UseQueryResult } from "@tanstack/react-query";
import { auth } from "@/lib/auth";
import { visits } from "@/visits/db";
import { listPhotos } from "@/visits/photos";
import type { Visit, VisitPhoto } from "@/visits/types";

export function useVisitList(): UseQueryResult<Visit[], Error> {
  const technicianId: string | null = auth.useAuthStore((state) => state.user?.id ?? null);

  return useQuery({
    queryKey: ["visits", "list", technicianId],
    enabled: technicianId !== null,
    networkMode: "always",
    queryFn: () =>
      visits.list(technicianId ?? undefined, { orderBy: "visited_at", reverse: true }),
  });
}

export function useVisit(visitId: string): UseQueryResult<Visit | null, Error> {
  return useQuery({
    queryKey: ["visits", "one", visitId],
    networkMode: "always",
    queryFn: async () => (await visits.get(visitId)) ?? null,
  });
}

export function useVisitPhotos(visitId: string): UseQueryResult<VisitPhoto[], Error> {
  return useQuery({
    queryKey: ["visits", "photos", visitId],
    networkMode: "always",
    queryFn: () => listPhotos(visitId),
  });
}

    Sem networkMode: \"always\", a lista fica carregando para sempre no pasto

    O TanStack Query pausa queries quando o navegador está offline — o padrão é networkMode: "online". Aqui a queryFn lê o IndexedDB, que não precisa de rede nenhuma, mas a query nem chega a rodar: a tela fica no skeleton até o sinal voltar. networkMode: "always" diz ao Query que essa função não depende de rede. A medição, e por que o SDK não troca o default do client inteiro, estão em Query → networkMode.

    O useOfflineSync inscreve o componente no motor: pending, syncing, lastSyncedAt e lastError mudam sozinhos a cada envio.     O logout chama resetWatermark(), não clearOutbox(). Apagar a fila perderia o dia de trabalho de quem saiu sem sinal.     8. A câmera

    // src/components/VisitPhotos.tsx
import { useQueryClient } from "@tanstack/react-query";
import { Camera } from "lucide-react";
import { Badge, Dropzone, EmptyState, Skeleton, StorageFullError, formatBytes, useToast } from "tempest-react-sdk";
import {
  bestSupportedType,
  resizeImage,
  useImagePreview,
  useImageProcessing,
} from "tempest-react-sdk/imaging";
import { addPhoto } from "@/visits/photos";
import { useVisitPhotos } from "@/visits/use-visits";
import type { VisitPhoto } from "@/visits/types";

function PhotoThumb({ photo }: { photo: VisitPhoto }) {
  const { url } = useImagePreview(photo.thumb);

  return (
    <figure style={{ margin: 0, display: "grid", gap: 4 }}>
      {url === null ? (
        <Skeleton height={96} />
      ) : (
        <img
          src={url}
          alt="Foto da vistoria"
          style={{ width: "100%", aspectRatio: "1", objectFit: "cover", borderRadius: 8 }}
        />
      )}
      <figcaption>
        <Badge size="sm" variant={photo.upload_url === null ? "warning" : "success"}>
          {photo.upload_url === null ? formatBytes(photo.bytes) : "Enviada"}
        </Badge>
      </figcaption>
    </figure>
  );
}

export function VisitPhotos({ visitId, disabled }: { visitId: string; disabled: boolean }) {
  const client = useQueryClient();
  const toast = useToast();
  const list = useVisitPhotos(visitId);
  const { compress, isWorking } = useImageProcessing();

  async function handleFiles(files: File[]): Promise<void> {
    const type = await bestSupportedType(["image/webp", "image/jpeg"]);

    for (const file of files) {
      try {
        const image = await compress(file, {
          maxBytes: 400_000,
          width: 1600,
          height: 1600,
          fit: "contain",
          withoutEnlargement: true,
          type,
        });
        const thumb = await resizeImage(image.blob, { width: 480, type });
        await addPhoto(visitId, image, thumb);
      } catch (error) {
        if (error instanceof StorageFullError) {
          toast.error("Memória cheia. Sincronize as visitas antes de tirar mais fotos.");
          break;
        }
        toast.error("Não deu para processar a foto. Tente fotografar de novo.");
      }
    }
    await client.invalidateQueries({ queryKey: ["visits", "photos", visitId] });
  }

  return (
    <section>
      <Dropzone
        accept="image/*"
        capture="environment"
        disabled={disabled || isWorking}
        onDrop={(files) => void handleFiles(files)}
      >
        <Camera size={18} aria-hidden /> {isWorking ? "Processando a foto…" : "Tirar foto"}
      </Dropzone>

      {list.isPending ? (
        <Skeleton height={96} style={{ marginTop: 12 }} />
      ) : list.isError ? (
        <p role="alert">Não deu para ler as fotos deste aparelho.</p>
      ) : list.data.length === 0 ? (
        <EmptyState
          title="Nenhuma foto"
          description="Fotografe bebedouros, cercas e o que mais o produtor precisar ver."
        />
      ) : (
        <div
          style={{
            display: "grid",
            gridTemplateColumns: "repeat(auto-fill, minmax(96px, 1fr))",
            gap: 8,
            marginTop: 12,
          }}
        >
          {list.data.map((photo) => (
            <PhotoThumb key={photo.id} photo={photo} />
          ))}
        </div>
      )}
    </section>
  );
}

    O capture="environment" do Dropzone abre o app de câmera do próprio celular, na câmera traseira. Você ganha foco, flash e resolução total sem pedir permissão nenhuma — e funciona no iPhone, onde nem todo navegador abre câmera dentro da página. No desktop o mesmo toque abre o seletor de arquivos, e arrastar uma foto para a área também vale.

    A foto de um celular atual tem vários MB. Guardar isso cru encheria o aparelho em poucos dias. Então ela passa pelo useImageProcessing antes:

    • width/height 1600 com fit: "contain" — reduzir é o que mais economiza;
    • maxBytes: 400_000 — o compress procura a qualidade que cabe no orçamento;
    • bestSupportedType — WebP onde o navegador sabe codificar, JPEG onde não. Pedir WebP a um navegador que não codifica devolveria PNG, várias vezes maior, sem erro nenhum.
    • resizeImage com width: 480 gera a miniatura da grade. Ela fica no aparelho depois do envio, quando o onUploaded libera a foto inteira.

    Comprimir antes do put é a alavanca mais barata contra o limite de espaço do navegador: cada foto ocupa o aparelho até subir, e no campo isso pode ser dias.

    O useImagePreview cria a URL de preview do Blob e a revoga sozinho no unmount.

    Quando o aparelho não tem mais espaço, o photos.put rejeita com StorageFullError, e o laço para: as próximas fotos também não caberiam, e a mensagem certa é "sincronize", não "fotografe de novo". O erro cru do navegador nem diria isso — no Chromium ele chega como AbortError do Dexie.

    Reencodar apaga o GPS da foto

    O EXIF some no reencode, incluindo as coordenadas. Isso protege a localização de quem fotografa — mas numa vistoria você quer saber onde a foto foi tirada. Por isso a localização vai no registro da visita, pelo useGeolocation, logo abaixo. Veja Imaging › Reencodar apaga o EXIF.

    Variante: visor dentro do app, com captureFrame

    Se a vistoria precisa de um enquadramento guiado (uma moldura para o brinco do animal, por exemplo), abra a câmera dentro da página e capture um frame do vídeo:

    // src/components/InlineCamera.tsx
import { Button, useCameraStream } from "tempest-react-sdk";
import { captureFrame, type CapturedFrame } from "tempest-react-sdk/imaging";

export function InlineCamera({ onShot }: { onShot: (frame: CapturedFrame) => void }) {
  const camera = useCameraStream({
    constraints: { video: { facingMode: "environment" }, audio: false },
  });

  async function shoot(): Promise<void> {
    const video = camera.videoRef.current;
    if (video === null) return;
    onShot(await captureFrame(video, { width: 1600, type: "image/jpeg", quality: 0.85 }));
  }

  if (camera.status === "error") {
    return (
      <div role="alert">
        <p>{camera.error?.message}</p>
        <Button onClick={camera.retry}>Tentar de novo</Button>
      </div>
    );
  }

  return (
    <>
      <video ref={camera.videoRef} muted playsInline style={{ width: "100%" }} />
      <Button fullWidth disabled={camera.status !== "ready"} onClick={() => void shoot()}>
        Capturar
      </Button>
    </>
  );
}

    O useCameraStream vem da raiz, que não exige o onnxruntime-web. O preço é outro: o frame sai na resolução do stream de vídeo, normalmente menor que a da câmera nativa. Para foto de vistoria, o <input capture> costuma ser a escolha melhor.

    O que acontece nessa tela:

    • Carregando: skeletons no formato do formulário enquanto o IndexedDB responde.
    • Erro: o ErrorState com "tentar de novo". Ler o próprio banco quase nunca falha — mas quando falha (cota estourada, modo privado), o técnico precisa saber.
    • Visita nova vs. existente: a rota é /visitas/:visitId, e o id já nasce na lista (crypto.randomUUID()). Se o banco não tem esse id, é visita nova.
    • GPS: o useGeolocation só liga em visita nova. O GPS do celular não precisa de internet — só de céu aberto, o que no pasto não falta. 🛰️
    • CPF: o CPFInput aplica a máscara e o validateCPF confere os dígitos antes de salvar.
    • Conflito e aprovada: o Alert explica o que houve. Em visita aprovada os campos ficam desabilitados e a barra de ações some.
    • Celular: a barra de ações fica fixa no rodapé, onde o polegar alcança, e o paddingBottom da página impede que ela cubra o último campo.

    11. Exportar a visita (sem rede)

    O produtor quer o relatório na hora, no WhatsApp dele. Não dá para esperar o servidor gerar um PDF à noite.

    // src/visits/export.ts
import { createZip, formatDateTime, writeXlsx } from "tempest-react-sdk";
import { listPhotos } from "@/visits/photos";
import type { Visit } from "@/visits/types";

function extensionOf(type: string): string {
  if (type === "image/webp") return "webp";
  if (type === "image/png") return "png";
  return "jpg";
}

function yesNo(value: boolean): string {
  return value ? "Sim" : "Não";
}

export async function buildVisitZip(
  visit: Visit,
  onPercent: (percent: number) => void,
): Promise<Blob> {
  const photoList = await listPhotos(visit.id);

  const sheet = writeXlsx(
    ["Campo", "Valor"],
    [
      ["Fazenda", visit.farm_name],
      ["Produtor", visit.producer_name],
      ["CPF do produtor", visit.producer_cpf],
      ["Data da visita", formatDateTime(visit.visited_at)],
      ["Cabeças no rebanho", visit.herd_size],
      ["Bebedouros limpos e com água", yesNo(visit.checklist.water)],
      ["Cercas e porteiras em bom estado", yesNo(visit.checklist.fences)],
      ["Vacinação em dia", yesNo(visit.checklist.vaccination)],
      ["Pastagem sem degradação", yesNo(visit.checklist.pasture)],
      ["Latitude", visit.latitude],
      ["Longitude", visit.longitude],
      ["Observações", visit.notes],
      ["Fotos", photoList.length],
    ],
  );

  return createZip(
    [
      { path: "visita.xlsx", data: sheet },
      ...photoList.map((photo, index) => ({
        path: `fotos/foto-${String(index + 1).padStart(2, "0")}.${extensionOf((photo.blob ?? photo.thumb).type)}`,
        data: photo.blob ?? photo.thumb,
      })),
    ],
    {
      onProgress: ({ loaded, total }) =>
        onPercent(total === 0 ? 100 : Math.round((loaded / total) * 100)),
    },
  );
}

    // src/components/ExportVisitButton.tsx
import { Share2 } from "lucide-react";
import { useState } from "react";
import { Button, Progress, shareOrDownloadBlob, useToast } from "tempest-react-sdk";
import { buildVisitZip } from "@/visits/export";
import type { Visit } from "@/visits/types";

export function ExportVisitButton({ visit }: { visit: Visit }) {
  const toast = useToast();
  const [percent, setPercent] = useState<number | null>(null);
  const [zip, setZip] = useState<Blob | null>(null);

  async function generate(): Promise<void> {
    setPercent(0);
    try {
      setZip(await buildVisitZip(visit, setPercent));
    } catch {
      toast.error("Não deu para montar o arquivo da visita.");
    } finally {
      setPercent(null);
    }
  }

  async function share(file: Blob): Promise<void> {
    await shareOrDownloadBlob(file, `visita-${visit.id.slice(0, 8)}.zip`, {
      title: `Visita — ${visit.farm_name}`,
    });
    setZip(null);
  }

  if (percent !== null) {
    return <Progress value={percent} showLabel label="Montando o arquivo" />;
  }
  if (zip !== null) {
    return (
      <Button size="sm" leftIcon={<Share2 size={16} />} onClick={() => void share(zip)}>
        Compartilhar
      </Button>
    );
  }
  return (
    <Button size="sm" variant="outline" onClick={() => void generate()}>
      Exportar
    </Button>
  );
}
    • O writeXlsx gera a planilha em memória. Número entra como número (o Excel soma), null vira célula vazia, acento sobrevive.
    • O createZip monta o arquivo em fatias, sem travar a tela, e guarda as fotos sem recomprimir — elas já são WebP/JPEG. O onProgress alimenta o Progress.
    • Foto que já subiu entra como miniatura: a inteira saiu do aparelho no onUploaded. No pasto, antes do sinal, o ZIP leva as fotos inteiras.
    • O shareOrDownloadBlob abre a folha de compartilhamento do celular (WhatsApp, e-mail, Drive) e baixa no desktop.

    Por que dois toques: \"Exportar\" e depois \"Compartilhar\"

    O navegador só abre a folha de compartilhamento logo depois de um toque do usuário (a ativação transitória). Montar um ZIP com dez fotos leva tempo, e ao fim dele essa janela pode ter fechado — aí o navigator.share recusa e o shareOrDownloadBlob cai no download. Separar "montar" de "compartilhar" faz o segundo toque abrir a folha na hora.

    O ZIP leva o CPF do produtor

    Dado pessoal saindo do app por WhatsApp é tratamento de dado pessoal sob a LGPD. Confirme com o jurídico da cooperativa que o produtor recebe o próprio relatório e que esse é um uso previsto. Se não precisar do CPF na planilha, tire a linha.

    12. O app e o service worker

    // src/App.tsx
import { useQueryClient } from "@tanstack/react-query";
import { useEffect } from "react";
import { BrowserRouter, Route, Routes } from "react-router";
import {
  Banner,
  Button,
  OfflineIndicator,
  formatBytes,
  QueryProvider,
  ToastProvider,
  UpdatePrompt,
  useOfflineSync,
  useServiceWorkerUpdate,
  useStorageEstimate,
} from "tempest-react-sdk";
import { VisitFormPage } from "@/pages/VisitFormPage";
import { VisitListPage } from "@/pages/VisitListPage";
import { visitSync } from "@/visits/sync";

function SyncRunner() {
  const client = useQueryClient();
  useOfflineSync(visitSync, { flushOnMount: true, flushOnOnline: true, intervalMs: 120_000 });

  useEffect(
    () =>
      visitSync.subscribe(() => {
        void client.invalidateQueries({ queryKey: ["visits"] });
      }),
    [client],
  );

  return null;
}

function StorageGuard() {
  const storage = useStorageEstimate({ pollMs: 60_000 });
  const { pending, pendingBytes } = useOfflineSync(visitSync, { flushOnOnline: false });

  if (storage.persisted === false && pending > 0) {
    return (
      <Banner
        variant="warning"
        title="Proteja as visitas deste aparelho"
        action={<Button size="sm" onClick={() => void storage.requestPersist()}>Proteger</Button>}
      >
        {formatBytes(pendingBytes)} em fotos ainda não foram enviadas. Sem proteção, o navegador
        pode apagá-las quando faltar espaço.
      </Banner>
    );
  }
  if (storage.ratio !== null && storage.ratio > 0.8) {
    return (
      <Banner variant="danger" title="Armazenamento quase cheio">
        {formatBytes(storage.usage)} de {formatBytes(storage.quota)} usados,{" "}
        {formatBytes(pendingBytes)} esperando envio. Envie as visitas pendentes antes de tirar
        mais fotos.
      </Banner>
    );
  }
  return null;
}

function ServiceWorkerGate() {
  const { updateAvailable, applyUpdate } = useServiceWorkerUpdate({ url: "/sw.js" });
  return <UpdatePrompt open={updateAvailable} onUpdate={applyUpdate} />;
}

export function App() {
  return (
    <QueryProvider>
      <ToastProvider position="top-center">
        <BrowserRouter>
          <OfflineIndicator position="top" />
          <StorageGuard />
          <SyncRunner />
          <Routes>
            <Route path="/" element={<VisitListPage />} />
            <Route path="/visitas/:visitId" element={<VisitFormPage />} />
          </Routes>
          <ServiceWorkerGate />
        </BrowserRouter>
      </ToastProvider>
    </QueryProvider>
  );
}

    • SyncRunner é o único lugar que dispara o envio: no boot, quando a rede volta e a cada dois minutos. O flush é single-flight, então gatilhos juntos viram um envio só. A cada mudança do motor ele invalida as queries ["visits"], e a lista mostra o badge novo sem recarregar.
    • StorageGuard junta o useStorageEstimate (quanto o aparelho usa e cabe) com o pendingBytes do motor (quanto disso é trabalho que ainda não existe em lugar nenhum). Sem armazenamento persistente o navegador pode despejar o IndexedDB sob pressão de disco; o signIn já pediu a proteção, e o banner só aparece se ela foi negada e há algo pendente.
    • OfflineIndicator mostra a barra de offline e pisca a confirmação quando o sinal volta.
    • UpdatePrompt pergunta antes de trocar de versão. Recarregar sozinho no meio de uma vistoria apagaria o que está digitado no formulário.
    • sw.ts só faz precache do app shell, para o app abrir sem rede. Veja PWA.

    Por que este sw.ts não tem installBackgroundSync

    Neste app, quem reenvia é a outbox, e o upload tus retoma sozinho. O template --pwa já deixa o tus fora do background sync; se você mantiver o installBackgroundSync do scaffold, acrescente "/api/visits/" ao RETRIED_BY_THE_PAGE do src/sw-sync-scope.ts, senão um PUT /api/visits/… que falhou offline sai pelas duas filas.     Testando no campo (sem ir ao campo)

    1. Abra o app no Chrome, entre e deixe o service worker instalar.
    2. DevTools → Network → Offline. Crie duas visitas com fotos. A lista mostra "Não enviada"; o badge do topo, "Offline".
    3. Recarregue a página ainda offline. Tudo continua lá — app shell do precache, dados do IndexedDB. ✅
    4. Troque para Slow 3G e salve. Durante o envio de uma foto, volte para Offline e depois para Slow 3G. Na aba Network, o upload retoma com um HEAD seguido de PATCH a partir do offset — não um POST novo.
    5. No servidor, marque uma visita como aprovada. Edite-a no app e salve: ela aparece como "Conflito", com a frase do servidor.

    Nenhuma visita perdida, nenhuma visita duplicada no servidor, e cada foto enviada uma vez, mesmo com quedas no meio.

    Recap

    • 🗄️ createOfflineDatabase guarda visitas e fotos (como Blob) na mesma base, com dono por técnico.
    • 📤 createOfflineSync é a outbox: saveVisit grava local e enfileira; o envio acontece quando der, e coalesce: true junta as edições da mesma visita num PUT só.
    • 📸 As fotos são attachments da visita: o motor as sobe com o upload resumível antes do deliver — falha retenta, queda retoma do offset, foto enviada não sobe de novo, e o onUploaded libera o arquivo do aparelho.
    • ⚖️ Conflito tem dois tipos: o que a máquina resolve (lastWriteWins no applyRemote) e o que o técnico resolve (409 VISIT_LOCKED vira estado conflict na tela).
    • 🗜️ useImageProcessing + bestSupportedType reduzem a foto no aparelho; o GPS vai no registro, porque o reencode apaga o EXIF.
    • 🟢 SyncStatusBadge, useOfflineSync e OfflineIndicator contam ao técnico o que está acontecendo; com foreignEntries: "hold", sair nunca arrisca a fila.
    • 📦 writeXlsx + createZip + shareOrDownloadBlob entregam o relatório sem rede.
    • 💾 StorageFullError separa "memória cheia" de "foto ruim" no catch da câmera.
    • 🔒 O login pede armazenamento persistente; useStorageEstimate + pendingBytes avisam quando falta espaço; o UpdatePrompt não troca de versão no meio da vistoria; o service worker só faz precache.
    • ⚠️ networkMode: "always" nas queries que leem o IndexedDB, senão elas pausam offline.
