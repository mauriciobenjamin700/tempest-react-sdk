    Upload resumível (tus)

    uploadWithProgress faz uma request. Isso funciona até o arquivo ficar grande: um áudio de 40 minutos gravado com useAudioRecorder, um vídeo, um dump. Aí um 4G que oscila por três segundos joga fora 300 MB já enviados, e recarregar a página joga fora tudo de novo.

    createResumableUpload divide o arquivo em chunks, guarda onde parou e continua — depois de uma queda de rede ou de um reload.

    Protocolo: tus 1.0.0, não um esquema nosso

    O cliente fala tus (core + as extensões creation e termination). Isso é deliberado: um cliente resumível de formato próprio obriga o backend a ser sempre nosso. Com tus você pode apontar para tusd, tus-node-server ou py-tus sem escrever servidor nenhum — e a seção O que o backend precisa implementar cabe numa tabela.

    Seção recipe-resumable-upload da gallery — rode localmente para interagir.

    O exemplo mínimo

    import { createResumableUpload, type ResumableUpload } from "tempest-react-sdk";
import { useRef, useState } from "react";

export function EnviarGravacao({ file }: { file: File }) {
  const upload = useRef<ResumableUpload | null>(null);
  const [percent, setPercent] = useState(0);
  const [state, setState] = useState("idle");

  async function start() {
    upload.current ??= createResumableUpload({
      endpoint: "/api/uploads",
      file,
      metadata: { filename: file.name },
      onProgress: ({ fraction }) => setPercent(Math.round(fraction * 100)),
      onStateChange: setState,
    });

    const done = await upload.current.start();
    if (done) await fetch(`/api/gravacoes?url=${encodeURIComponent(done.url)}`, { method: "POST" });
  }

  return (
    <>
      <progress value={percent} max={100} />
      <button type="button" onClick={() => void start()}>Enviar</button>
      <button type="button" onClick={() => upload.current?.pause()}>Pausar</button>
      <button type="button" onClick={() => void upload.current?.resume()}>Continuar</button>
      <button type="button" onClick={() => void upload.current?.abort({ discard: true })}>
        Cancelar
      </button>
      <p>{state}</p>
    </>
  );
}

    O que acontece: um POST cria o upload, uma sequência de PATCH empurra 5 MiB por vez, onProgress recebe cada tick de bytes, e no fim start() resolve com { url, size } — a URL tus, que você grava junto do registro.

    start() resolve null quando você pausou ou cancelou

    Só uma falha rejeita. pause() e abort() não são falhas, então a promessa resolve null e você não precisa de try/catch em volta de um botão de pausar.

    Estados

    upload.state (e o onStateChange) passa por:

    Estado Significado
    idle Nada começou
    creating O POST de criação está em voo
    uploading Chunks indo
    paused pause() — o ponto de retomada fica guardado
    done Terminou; o registro persistido foi apagado
    error As tentativas acabaram; start() rejeitou
    aborted abort() — com discard: true, o registro foi apagado

    Retomar depois de um reload

    É o motivo de existir. O cliente guarda { url, offset, size, idempotencyKey } (e o owner, com getPrincipal ou getToken) sob uma chave de retomada e, no próximo start(), reencontra o upload:

    const upload = createResumableUpload({ endpoint: "/api/uploads", file });
// Recarregou a página, o usuário escolheu o mesmo arquivo, chamou start() de novo:
// → HEAD no upload antigo, offset volta em 312 MB, os PATCH continuam de lá.

    A chave padrão é uma impressão digital de endpoint + nome + tamanho + tipo + lastModified — o mesmo critério dos clientes tus de referência. Barato (não hasheia 400 MB) e muda sempre que o arquivo muda, que é a propriedade importante: retomar dentro do arquivo errado corromperia os dois.

    Um Blob sem nome tem impressão digital fraca

    Blob não tem name nem lastModified, então dois blobs do mesmo tamanho e tipo colidem. Passe key explícito quando o que você envia não é um File.

    Onde o estado mora

    Por padrão, localStorage, via createLocalUploadStorage(). Não IndexedDB, e isso é escolha: o registro tem quatro campos e uma URL, o requisito é só sobreviver a um reload, e puxar Dexie pra isso colocaria IndexedDB no bundle de todo app que envia um arquivo.

    Se o seu app já tem um banco Dexie aberto, plugue o seu:

    import {
  createOfflineStore,
  createResumableUpload,
  type ResumableUploadRecord,
} from "tempest-react-sdk";

const store = createOfflineStore<{ id: string; record: ResumableUploadRecord }, string>({
  databaseName: "Uploads",
  version: 1,
  tableName: "resume",
  indexes: "&id",
});

createResumableUpload({
  endpoint: "/api/uploads",
  file,
  storage: {
    get: async (key) => (await store.get(key))?.record ?? null,
    set: async (key, record) => {
      await store.put({ id: key, record });
    },
    delete: async (key) => {
      await store.delete(key);
    },
  },
});

    Um storage assíncrono pode implementar também deleteIf(key, matches): apaga o registro só se matches aceitar o que está gravado agora, lendo e apagando numa transação só. O upload o usa para esquecer o registro de um run cuja conta saiu, e sem ele cai em get seguido de delete — entre os dois, a conta seguinte pode ter gravado o próprio registro sob a mesma chave, e é esse que seria apagado (o upload dela recomeçaria do zero; #657). O createLocalUploadStorage() já traz o deleteIf, e por ser síncrono não precisa de mais nada.

    storage: null desliga a persistência: aí a retomada sobrevive a uma queda de rede, mas não a um reload.

    Um registro por usuário — getPrincipal e clear()

    O registro sobrevive ao reload — e, por isso mesmo, ao logout. A chave padrão não tem usuário nenhum: se A sai deixando um upload pela metade e B escolhe um arquivo com a mesma impressão digital, o cliente de B faria HEAD e PATCH na URL de upload de A com o token de B e, se o servidor recusasse, mandaria o POST de criação com a Idempotency-Key de A (#479).

    Duas peças fecham isso:

    import { createLocalUploadStorage, createResumableUpload } from "tempest-react-sdk";

declare const file: File;
declare const auth: { getToken: () => string | null };
declare const session: { userId: string | null };

const upload = createResumableUpload({
  endpoint: "/api/uploads",
  file,
  getToken: () => auth.getToken(),
  getPrincipal: () => session.userId,
});

await upload.start();

export function onSessionEnd(): void {
  createLocalUploadStorage().clear();
}
    • getPrincipal — o mesmo getter do reporter de erros e do provideBackgroundSyncCredentials. O registro ganha uma impressão digital de mão única do usuário (owner, nunca o id em claro), e um registro de outro dono — outro usuário, ninguém, ou sem dono, gravado antes da 0.78.0 — é apagado em vez de retomado: a URL dele não recebe request, e a Idempotency-Key dele nunca é reaproveitada.
    • clear() — apaga todo registro sob o prefixo tempest-upload: do createLocalUploadStorage(). Chame no onSessionEnd (veja Auth → Fim de sessão). Um storage próprio implementa o equivalente do lado dele.

    E se a troca de conta acontece com o upload rodando? O getPrincipal é relido antes de cada chunk e de cada gravação do registro: quando ele passa a apontar outra pessoa, o run para com ResumableUploadSupersededError (reason: "principal"), antes de o token da conta nova ir para a URL de upload da anterior. Um clear() no meio do run faz o mesmo (reason: "cleared") em vez de o registro ser regravado. Não é pausa — o run não pode continuar como a conta nova: o estado vai para "error".

    Desde a 0.88.0 a checagem também roda quando cada resposta chega (#642). Uma resposta que a request de A recebeu depois da troca — chunk confirmado, criação recusada com o envelope de erro de A, o HEAD de offset — rejeita com ResumableUploadSupersededError em vez de cair no catch de B com os dados de A; e um HEAD respondido depois da troca não cai mais na criação com o bearer de B e a Idempotency-Key de A. Com reason: "principal", o registro que o run gravou para A também é apagado: ele guarda a URL do upload de A — que muitos servidores tus tratam como a credencial — e a chave de A, agora no storage de B, e ninguém pode usá-lo (o carimbo impede B de adotá-lo, e a sessão do auth.getToken não volta com a mesma chave). Um registro que B gravou na mesma chave enquanto isso fica. Até a 0.87.0 o registro de A ficava como estava.

    import { ResumableUploadSupersededError, createResumableUpload } from "tempest-react-sdk";

declare const file: File;
declare const session: { userId: string | null };

export async function send(): Promise<string | null> {
  const upload = createResumableUpload({
    endpoint: "/api/uploads",
    file,
    getPrincipal: () => session.userId,
  });
  try {
    return (await upload.start())?.url ?? null;
  } catch (error) {
    if (error instanceof ResumableUploadSupersededError) return null;
    throw error;
  }
}

    O clear() só apaga valor com formato de registro de upload: um prefixo sem delimitador ("app") não leva junto as chaves do próprio app ("appSettings").

    Sem getPrincipal: o registro é do token (0.82.0)

    Até a 0.81.0, quem não passava getPrincipal retomava qualquer registro com a mesma chave, de qualquer usuário (#528). Desde a 0.82.0, com getToken e sem getPrincipal, o registro é carimbado com uma impressão digital de mão única do token (owner: "t:…", nunca o token em claro), e um registro carimbado por outro token — ou sem carimbo — é apagado em vez de retomado. B nunca mais manda HEAD para a URL de A nem reaproveita a Idempotency-Key de A.

    O preço é que token gira. O carimbo é refeito a cada gravação do registro, e o próprio handle continua o seu upload depois de um refresh (pause() → resume()). Mas um reload depois de um refresh em que nenhum chunk foi gravado encontra o carimbo do token velho e recomeça do zero. O getPrincipal não tem esse custo — o usuário não gira —, então continua sendo o recomendado:

    Configuração Registro de outro usuário Retoma depois de refresh + reload Troca de conta com o upload rodando
    getPrincipal apagado sim para com ResumableUploadSupersededError
    getToken: auth.getToken do createTempestAuth (0.82.0) apagado sim para com ResumableUploadSupersededError
    só getToken, qualquer outro getter (padrão 0.82.0) apagado só se um chunk foi gravado depois do refresh continua, com o token novo na URL do upload anterior
    nenhum dos dois (anônimo, sessão por cookie) retomado sim continua

    Com um getter qualquer, o handle não distingue um refresh de um login de outra conta — os dois são só um token novo. Por isso o abort() encerra também a exceção do registro próprio: um start()/resume() depois dele se comporta como um handle novo, que só retoma o registro se o dono atual o carimbou e, senão, cria outro upload com Idempotency-Key nova. Até a 0.82.0, o resume() depois do abort() que esta página manda chamar no onSessionEnd continuava "o próprio upload" com o token de quem estivesse logado — o de B, na URL de A, com a Idempotency-Key de A (#561). Sem abort(), a linha acima continua valendo: troque o getter por auth.getToken ou passe getPrincipal.

    getToken: auth.getToken — o registro é da sessão

    Quando o getToken é o próprio getter que o createTempestAuth devolveu, o upload lê dele a sessão do preset (auth.sessionKey()) e a usa como getPrincipal. A sessão não gira no refresh, então o reload depois de uma rotação retoma; e ela muda no login() de outra conta, então o run para antes de o token novo chegar à URL do upload anterior:

    import { createResumableUpload, createTempestAuth } from "tempest-react-sdk";

export const auth = createTempestAuth({ baseURL: "https://api.exemplo.com" });

export function enviarGravacao(gravacao: File) {
  return createResumableUpload({
    endpoint: "/api/uploads",
    file: gravacao,
    getToken: auth.getToken,
  }).start();
}

    Vale também para sessão restaurada por auth.refresh() — o restore do boot por cookie, o callback de OAuth: desde a 0.83.0 ela ganha sessão própria, e a conta seguinte restaurada do mesmo jeito não retoma o upload da anterior (até a 0.82.0 as duas respondiam a mesma chave, ver auth.sessionKey()).

    Medido em src/http/resumable-upload.session.test.ts (npx vitest run src/http/resumable-upload.session.test.ts): na main antes desta mudança, um login() de B entre o primeiro e o segundo PATCH fazia o upload terminar, com os PATCH seguintes levando Bearer B-tok-1 para a URL do upload de A; e o reload depois de um refresh recomeçava com um POST novo. Agora o run rejeita com ResumableUploadSupersededError e o reload retoma com HEAD.

    O getter, não um wrapper

    getToken: () => auth.getToken() é outra função e não carrega a sessão: continua amarrado ao token, como a linha "qualquer outro getter" da tabela. Um login() na mesma conta é sessão nova — o upload recomeça; para retomar através de logins, passe getPrincipal com o id do usuário. Num build de desenvolvimento, getToken sem getPrincipal que não seja o getter do preset gera um console.warn (uma vez por getter, #657) — produção fica em silêncio.

    Sessão por cookie: clear() no fim de sessão, ou getPrincipal

    Sem getToken — sessão só por cookie, fora do createTempestAuth, que sempre tem token — o SDK não enxerga quem está logado: o cookie é HttpOnly, e nada no navegador avisa a troca de conta. O registro fica sem dono e é retomado por quem vier depois. O teardown que alcança esse caso é o createLocalUploadStorage().clear() no fim de sessão, e ele basta: apaga os registros, para o run em andamento (reason: "cleared") e, desde a 0.84.0, faz o handle pausado antes dele recomeçar com Idempotency-Key nova em vez de levar a da sessão anterior para a criação do upload da conta seguinte (#528 — até a 0.83.0 o resume() de B reaproveitava a chave de A). O abort() deixa de ser necessário aqui. Para retomar entre reloads sem depender do teardown, passe getPrincipal.

    Se cruzar contas ainda depende do servidor tus. A partir da 0.370.0 o tempest-fastapi-sdk tem servidor tus (make_tus_router): com current_user_id configurado, só o dono do upload sonda, continua ou apaga a URL, e qualquer outra conta recebe 404 TUS_UPLOAD_NOT_FOUND; sem current_user_id, o upload é anônimo e a URL é a única credencial. Com outro servidor tus (como o tusd), quem autoriza HEAD/PATCH é ele — muitos tratam a URL como a própria credencial. O IdempotencyMiddleware dele, por outro lado, escopa a chave pelo digest de Authorization, Cookie, X-Token e X-API-Key: a chave de A repetida por B não devolve o upload de A.

    A falha que realmente acontece

    Não é o chunk que se perde. É o chunk que o servidor gravou e cuja resposta não voltou. O cliente não distingue isso de um chunk perdido, e reenviar às cegas duplicaria bytes.

    Duas coisas impedem:

    1. Escritas são endereçadas, não anexadas. Todo PATCH declara o offset em que escreve (Upload-Offset). Se a resposta se perdeu e o cliente repetir, ele está pedindo pra escrever bytes que o servidor já tem — e leva 409. Em qualquer retentativa, o cliente relê a verdade com HEAD antes de escrever e continua de onde o servidor realmente está.

    2. A criação leva Idempotency-Key. O tus não tem criação idempotente; sem isso, um 201 perdido deixaria um upload órfão no servidor e o cliente criaria um segundo. A chave (de generateIdempotencyKey) é gravada antes da primeira tentativa e reusada na retentativa. Backend que honra o header devolve o mesmo Location; backend que ignora funciona igual, só fica com o órfão.

    O backoff é o retry do SDK

    Não existe um segundo backoff aqui: cada chunk roda dentro do retry — exponencial, com Retry-After respeitado. Ajuste por retry: { retries, initialDelay, shouldRetry }.

    O que o loop de chunk retenta, e o que não

    Duas decisões são específicas do protocolo de retomada e não seguem a política geral do SDK:

    Resposta Retenta? Por quê
    falha de rede, 408, 425, 429, 5xx sim política padrão: pode mudar sozinho
    409, 412 sim é o sinal de offset divergente — o replay é a correção, e o HEAD de resync a executa
    200/204 com Upload-Offset que não passou do enviado sim, dentro do retries o tus manda o offset novo ser o anterior mais os bytes recebidos; confirmar sem avançar é erro de protocolo (code: "UPLOAD_OFFSET_STALLED", 0.83.0). O HEAD de resync confere se o servidor gravou mesmo assim
    404, 410 não o upload sumiu do servidor. Recriar só acontece no attach, nunca dentro do loop
    400, 403, 413, 415, 422 não recusa deliberada; a 5ª tentativa recebe a mesma resposta

    O 409 é o caso interessante: a política geral do SDK recusa 4xx, e com razão — mas aqui ele significa "seu offset está errado", que é exatamente o que a retentativa conserta.

    O 404 é o inverso. Recurso que desapareceu parece transitório, mas o HEAD de resync bate no mesmo 404, então retentar era sondar um recurso morto cinco vezes e só então mostrar "o upload expirou" — com o backoff somado em cima. Nesse caso, comece um upload novo.

    Um shouldRetry seu substitui essa política inteira, nas duas direções.

    O que o backend precisa implementar

    Toda request leva Tus-Resumable: 1.0.0.

    Passo Request Resposta esperada
    Criar POST {endpoint} + Upload-Length, Upload-Metadata, Idempotency-Key 201 + Location (URL do upload, absoluta ou relativa)
    Sondar HEAD {uploadUrl} 200/204 + Upload-Offset
    Escrever PATCH {uploadUrl} + Upload-Offset, Content-Type: application/offset+octet-stream, corpo = chunk 204 + o novo Upload-Offset, maior que o enviado; 409 quando o offset não bate
    Descartar DELETE {uploadUrl} 204

    Detalhes que costumam morder:

    • Location pode ser relativo. O cliente resolve contra o endpoint para onde o POST foi (RFC 9110), então /files/abc vindo de https://tus.exemplo.com/files/ vira https://tus.exemplo.com/files/abc. Até a 0.81.0 resolvia contra a página e mandava os chunks para a origem do app.
    • Upload-Metadata é chave base64(valor) separado por vírgula, com o valor em UTF-8 antes do base64 — é assim que nota-ação.webm sobrevive a um header HTTP.
    • HEAD respondendo 404/410 é lido como "o servidor esqueceu esse upload": o cliente recria do zero em vez de travar.
    • Upload-Offset ausente num PATCH bem-sucedido é tolerado — o cliente assume o fim do chunk —, mas mandar é melhor.
    • Upload-Offset que não avança num PATCH bem-sucedido — o mesmo offset enviado, ou menor — vira TempestApiError com code: "UPLOAD_OFFSET_STALLED" e o status da resposta, contado como falha do chunk: a próxima tentativa relê o offset com HEAD, e o upload rejeita quando o retries acaba (retries: 0 manda um PATCH; o padrão, cinco). Até a 0.82.0 o loop aceitava a resposta como sucesso e reenviava o mesmo chunk para sempre — medido no #569, mais de 1500 requisições em 4 s mesmo com retries: 0; o caso real foi um redirect 303 que virou GET respondido 200 com o mesmo offset. Recusar sem retentativa foi descartado: o servidor pode ter gravado e só respondido mal, e o HEAD resolve isso de graça. É a mesma regra do cliente de referência (tus-js-client), em que só um offset que andou recarrega o contador de retentativas.
    • Reflita o Idempotency-Key numa tabela de chaves se quiser evitar órfãos.

    Servidor pronto

    tusd (Go), tus-node-server (Node) e tuspy/py-tus (Python) já implementam a tabela. Num FastAPI próprio são quatro rotas.

    Progresso e pausa, com precisão

    const upload = createResumableUpload({
  endpoint: "/api/uploads",
  file,
  chunkSize: 1024 * 1024, // 1 MiB: tick mais fino, mais round-trips
  // o padrão é DEFAULT_CHUNK_SIZE (5 MiB), exportado para uma tela de ajustes exibir
  getToken: () => auth.getToken(),
  withCredentials: true,
  retry: { retries: 8, initialDelay: 500 },
  onProgress: ({ loaded, total, fraction, resumedFrom }) => {
    console.log(`${loaded}/${total} (${Math.round(fraction * 100)}%), retomou em ${resumedFrom}`);
  },
});
    • onProgress recebe bytes do arquivo inteiro, não do chunk. resumedFrom diz quantos já estavam no servidor quando esta execução começou — útil pra não anunciar "0%" num upload que retomou em 80%.
    • pause() derruba o chunk em voo; o offset persistido continua o do último chunk confirmado. O resume() faz HEAD primeiro, então bytes parciais que o servidor aceitou não se perdem.
    • abort({ discard: true }) manda DELETE e apaga o registro; sem discard, o ponto de retomada fica. Num handle de antes de uma troca de conta (o getPrincipal/sessão mudou, ou o storage foi limpo), o descarte não vai ao servidor — o DELETE sairia com a credencial da conta nova — e só apaga o registro se ele ainda for deste upload: o registro que a outra conta gravou sob a mesma chave (o fingerprint do arquivo) fica. O abort() sem discard num handle assim também apaga o registro deste upload (com chunk em voo ou pausado): ninguém mais pode retomá-lo, e ele guardava a URL e a Idempotency-Key da conta anterior no storage da seguinte até um clear() (#657). Vale também para o handle sem vínculo (sessão por cookie ou upload anônimo, sem getToken nem getPrincipal): guardado de antes de um clear(), o descarte dele não manda DELETE e deixa o registro da sessão seguinte — até a 0.90.0 ele saía com os cookies da conta nova e apagava o registro dela (auditoria run-17). Um getPrincipal que lança no abort() conta como dono mudado: nada vai ao servidor, e o abort() não rejeita. E um handle que já rodou só apaga o registro com a própria Idempotency-Key, mesmo quando não enxerga a troca: um handle amarrado só a um getToken próprio (sem getPrincipal, sem o getter do createTempestAuth, sem clear() no fim da sessão) apagava o registro que a conta seguinte gravou para o mesmo arquivo — até a 0.91.0 (#684). O DELETE desse handle ainda sai para a URL de upload da conta anterior, com a credencial atual: só o servidor pode recusá-lo, por isso passe getPrincipal ou o getToken do createTempestAuth. Um handle que nunca rodou segue apagando o registro do arquivo.

    O token não segue o Location para fora da sua origem

    O tus responde a criação com um Location que o servidor escolhe, e o spec permite que seja uma URL absoluta em outro host — entregar o upload a um storage é operação normal, não ataque. Até a 0.65.0 o bearer token seguia aquele header para onde ele apontasse, junto com os bytes do arquivo.

    Desde a 0.66.0 a credencial fica presa à origem do endpoint. Se o Location aponta para outra origem, o POST de criação ainda leva o token — ele foi para o seu backend —, e os HEAD/PATCH/DELETE seguintes vão sem ele. O upload termina normalmente, que é o que uma URL de storage pré-assinada espera.

    Quando o storage realmente precisa do token da sua API, declare:

    createResumableUpload({
  endpoint: "/api/uploads",
  file,
  getToken: () => auth.getToken(),
  trustedOrigins: ["https://storage.exemplo.com"],
});

    Vale também para o registro persistido: uma url guardada no localStorage apontando para fora não recupera o token na retomada.

    Desde a 0.82.0 os headers fixos seguem o mesmo escopo: um X-Api-Key vai no POST de criação e não vai para um Location em outra origem, que recebe só os headers do tus.

    A opção csrf segue a mesma regra: o token CSRF vai no POST de criação, em cada PATCH e no DELETE do descarte — nunca no HEAD de offset — e só para a origem do endpoint e as trustedOrigins. Ver CSRF.

    XMLHttpRequest, não fetch — menos quando há headers fixos

    Como em uploadWithProgress: fetch ainda não reporta progresso de upload em navegador nenhum. Aqui há um segundo motivo — o tus devolve o novo offset num header de resposta, e uploadWithProgress só entrega corpo parseado, então não dava pra reaproveitar.

    A exceção é a requisição que leva os headers fixos (desde a 0.83.0, #564). O XMLHttpRequest segue todo redirect e não tem modo de recusar. Medido no Chrome 150 com o createResumableUpload empacotado (tarball do npm pack empacotado com esbuild), servidor em 127.0.0.1:5340 respondendo 301/302/303/307/308 para localhost:5341, que ecoa os headers com CORS: o X-Api-Key chegou à outra origem nos 5 códigos, no POST de criação e no PATCH do chunk, junto com os bytes; o X-CSRF-Token também; só o Authorization o navegador tirou. O responseURL do XHR mostra onde a requisição terminou (http://localhost:5341/files/1, medido), mas quando dá para lê-lo o header já foi.

    Então essa requisição sai por fetch com redirect: "manual", e um redirect como resposta vira TempestApiError com code: "REDIRECT_REFUSED", sem retentativa — a mesma regra do createApiClient (HTTP). Remedido depois da mudança: nenhuma requisição chegou à outra origem nos 10 casos (5 códigos × redirect no PATCH e na criação), e um endpoint em outra origem sem redirect continua funcionando.

    O preço é o progresso dentro do chunk: com headers fixos, o onProgress avança uma vez por chunk confirmado. Para uma barra mais fina, baixe o chunkSize; ou mande a credencial pelo getToken, que mantém o XMLHttpRequest — o Authorization o navegador tira sozinho num redirect para outra origem. O X-CSRF-Token sozinho não troca o transporte, pelo motivo que o HTTP documenta para o createApiClient.

    Migração: um servidor que responde a criação ou o chunk com redirect — inclusive de mesma origem, como o 307 de barra final do FastAPI — passa a falhar com REDIRECT_REFUSED quando há headers fixos. Aponte o endpoint para a URL final (/api/uploads/).

    Resumo

    • createResumableUpload({ endpoint, file }) — chunks de 5 MiB, retomada por rede e por reload, protocolo tus 1.0.0.
    • start() / pause() / resume() / abort({ discard }); start() resolve null quando você parou de propósito.
    • O ponto de retomada mora em localStorage por padrão; troque por storage, desligue com null.
    • getPrincipal prende o registro ao usuário; sem ele, desde a 0.82.0, o registro é do token de getToken — ou da sessão, quando o getter é o auth.getToken do createTempestAuth. createLocalUploadStorage().clear() no onSessionEnd apaga os que sobraram.
    • Resposta perdida é resolvida por offset endereçado + HEAD antes de cada retentativa, e a criação por Idempotency-Key.
    • Backoff é o retry do SDK — não existe um segundo.
