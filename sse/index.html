    Server-Sent Events

    Wrapper sobre EventSource com reconnect exponencial, heartbeat opt-in e parsing JSON. Caso de uso original: stream de notificações (NEW-ALO, PAYMENT-SUCCESS, etc.) do alofans-frontend.

    SSE vs WebSocket — qual escolher?

    SSE é unidirecional (servidor → cliente), roda sobre HTTP comum, reconecta sozinho e autentica por cookie sem cerimônia. Se o cliente não precisa enviar mensagens, SSE é mais simples e barato. Pra tráfego bidirecional (chat, colaboração), use WebSocket.

    Seção recipe-realtime da gallery — rode localmente para interagir.

    Quando usar

    • Push unilateral servidor → cliente, sem necessidade de envio do cliente.
    • Reconexão automática barata.
    • Autenticação por cookie (withCredentials: true) num backend que lê o cookie no próprio stream.

    Backend tempest-fastapi-sdk >= 0.331.0: o stream não lê cookie

    O router SSE pronto do backend abre o stream só com ?ticket= (ou Authorization: Bearer, que o EventSource não manda). O cookie de sessão vale no pedido do ticket, não no stream. Para esse backend, use useTicketEventStream — com sessão em header ou em cookie.

    API imperativa — createEventStream

    Use fora de React (services, inicialização) quando você gerencia o ciclo de vida na mão:

    import { createEventStream } from "tempest-react-sdk";

interface StreamEvent {
  type: "NOTIFY" | "PAYMENT-SUCCESS";
  message: string;
}

const stream = createEventStream<StreamEvent>(
  `${import.meta.env.VITE_API_URL}/notifications/stream`,
  {
    withCredentials: true,
    namedEvents: ["notification", "payment"],
    heartbeatEvents: ["ping"],
    maxRetries: 10,
    onOpen: () => console.log("SSE aberto"),
    onMessage: ({ event, data, id }) => {
      if (event === "payment") handlePayment(data);
      else addNotification(data);
    },
    onStatusChange: (status) => console.log("SSE", status),
    onError: (err) => console.error(err),
  },
);

// Mais tarde, ao desmontar / deslogar:
stream.close();

// Forçar reconexão imediata (zera o contador de tentativas):
stream.reconnect();

// Ler o status atual:
console.log(stream.status);

    Cada onMessage recebe { event, data, id, raw }: event é o nome do evento SSE (default "message"), data já vem JSON-parsed (com fallback pra string crua), id é o lastEventId do servidor e raw é o MessageEvent original.

    Reconexão e heartbeat

    Backoff: 1s → 2s → 4s → 8s → ... (limitado em 30s), até maxRetries (default 10)
    • A cada erro o stream fecha, agenda reconexão com backoff exponencial e emite status "closed". Ao reabrir com sucesso, o contador zera.
    • Esgotadas as maxRetries, o status vira "error" e o stream para de tentar.
    • Eventos listados em heartbeatEvents (default ["ping"]) não disparam onMessage — só mantêm o socket vivo.

    Configure os heartbeatEvents conforme seu backend

    Se o servidor envia keep-alives sob outro nome de evento (ex.: "keepalive"), liste-o em heartbeatEvents pra não poluir o onMessage com pings.

    Hook — useEventStream

    Dentro de componentes, o hook amarra o ciclo de vida do stream ao componente — abre na montagem, fecha no unmount:

    import { useEventStream } from "tempest-react-sdk";

interface Notification {
  id: string;
  message: string;
}

export function NotificationListener({ user }: { user: { id: string } | null }) {
  const { status, lastMessage, reconnect } = useEventStream<Notification>(
    `${import.meta.env.VITE_API_URL}/notifications/stream`,
    {
      enabled: !!user, // só conecta quando o usuário existe
      withCredentials: true,
      onMessage: ({ data }) => addToInbox(data),
    },
  );

  return (
    <div>
      <span>Stream: {status}</span>
      {status === "error" && <button onClick={reconnect}>Reconectar</button>}
      {lastMessage && <p>Última: {lastMessage.data.message}</p>}
    </div>
  );
}
    • enabled: false desconecta o stream (use enquanto espera o user carregar).
    • sessionKey (o id do usuário) amarra o stream à sessão: trocar de conta fecha o stream e zera lastMessage — ver troca de conta. Com client: auth.api do createTempestAuth, isso é automático no useTicketEventStream.
    • Mudar a URL re-abre a conexão; mudar o onMessage não (callback via ref interna — sem reconexões à toa).
    • lastMessage guarda a última mensagem recebida (heartbeats não contam).
    • Cleanup automático no unmount.

    error significa que esgotou as tentativas

    Quando o status chega em "error", o stream desistiu sozinho. Ofereça um botão chamando reconnect() (que zera o contador) em vez de esperar uma reconexão automática que não vem mais.

    Autenticação por ticket — useTicketEventStream

    EventSource não manda header. Durante muito tempo o jeito de autenticar o stream foi pôr o access token na URL (?access_token=…), que acaba no log de todo proxy no caminho. O tempest-fastapi-sdk 0.331.0 trocou isso por um ticket: uma chamada autenticada normal pede um JWT de vida curta, e só ele vai na URL do stream.

    Rota do backend O que faz
    POST /sse/ticket autenticada (header ou cookie). Responde { "ticket": "<jwt>", "expires_in": 60 }
    GET /sse/stream?ticket=<jwt> abre o stream; o canal vem de dentro do ticket. Aceita ?ticket= ou Authorization: Bearer — não lê cookie

    O helper faz as duas chamadas para você — e as repete a cada reconexão:

    import { createApiClient, useTicketEventStream } from "tempest-react-sdk";
import { z } from "zod";

const api = createApiClient({
    baseURL: "https://api.exemplo.com",
    prefix: "/api",
    getToken: () => localStorage.getItem("token"),
});

const notificacaoSchema = z.object({ id: z.string(), message: z.string() });

type Notificacao = z.infer<typeof notificacaoSchema>;

export function Notificacoes({ logado }: { logado: boolean }) {
    const { status, lastMessage, reconnect } = useTicketEventStream<Notificacao>({
        client: api,
        enabled: logado,
        schema: notificacaoSchema,
        onUrlError: (erro) => console.warn("ticket recusado:", erro),
    });

    return (
        <div>
            <span>Stream: {status}</span>
            {status === "error" && <button onClick={reconnect}>Reconectar</button>}
            {lastMessage && <p>{lastMessage.data.message}</p>}
        </div>
    );
}
    1. O ticket é pedido pelo api: sai com Authorization (ou com o cookie de sessão e o X-CSRF-Token), e um 401 passa pelo refresh do cliente antes de chegar aqui.
    2. A URL do stream é montada com api.url("/sse/stream", { ticket }) — mesmo baseURL, mesmo prefix. O access token nunca entra nela.
    3. Toda reconexão pede um ticket novo. O ticket só abre stream por expires_in segundos; reconectar com o antigo depois disso é um 401.

    O que passa na rede, do primeiro stream até uma queda depois do vencimento do ticket:

    POST https://api.exemplo.com/api/sse/ticket                   200  {"ticket":"eyJ…A","expires_in":60}
GET  https://api.exemplo.com/api/sse/stream?ticket=eyJ…A      200  text/event-stream
     … 3 min depois a rede cai; backoff de 1 s …
POST https://api.exemplo.com/api/sse/ticket                   200  {"ticket":"eyJ…B","expires_in":60}
GET  https://api.exemplo.com/api/sse/stream?ticket=eyJ…B      200  text/event-stream

    O stream aberto não cai quando o ticket vence — o ticket só vale para abrir. Quem precisa de um novo é a reconexão, e é ela que o pede.

    Por que useEventStream com uma URL fixa não serve aqui

    Com useEventStream(`${API}/sse/stream?ticket=${ticket}`) o primeiro stream abre, mas a reconexão reusa a mesma string. Se a rede cair depois dos 60 s, o backend responde 401 a cada tentativa, o stream gasta as maxRetries nisso e termina em "error" — com o usuário ainda logado.

    Sessão em cookie

    Se o login guarda a sessão em cookie (AUTH_TOKEN_DELIVERY="cookie" no backend), o ticket sai do mesmo jeito — só o cliente muda. O POST /ticket é uma escrita, então o cookie precisa do par CSRF:

    import { createApiClient, useTicketEventStream } from "tempest-react-sdk";

const api = createApiClient({
    baseURL: "https://api.exemplo.com",
    prefix: "/api",
    withCredentials: true,
    csrf: true,
});

export function Pedidos({ logado }: { logado: boolean }) {
    const { status } = useTicketEventStream<{ id: string; status: string }>({
        client: api,
        enabled: logado,
        onMessage: ({ data }) => console.log("pedido", data.id, data.status),
    });

    return <span>Stream: {status}</span>;
}

    O cookie vai no POST /ticket (com X-CSRF-Token, ecoado do cookie csrf_token); o GET /stream leva só o ticket. Detalhes do csrf em HTTP → CSRF.

    Com um pedido mudando de status no backend, o console mostra:

    pedido 8f2c pago
pedido 8f2c enviado

    Quando o ticket é recusado

    Um ticket negado com status que nenhuma espera resolve não é re-tentado: o stream vai direto para status: "error" e onUrlError recebe o TempestApiError.

    Falha ao pedir o ticket O que acontece
    rede, timeout, 429, 5xx nova tentativa com o backoff de sempre
    401 (depois do refresh do cliente) para em "error" — a sessão acabou
    403 ACCOUNT_INACTIVE para em "error" — conta desativada
    resposta sem ticket para em "error" — contrato diferente do esperado

    A política é isRetriableTicketError; passe shouldRetryUrl para trocar.

    Uma conta desativada, por exemplo, termina assim — uma requisição só, sem stream e sem nova tentativa:

    POST https://api.exemplo.com/api/sse/ticket   403  {"detail":"…","code":"ACCOUNT_INACTIVE"}
status: "connecting" → "error"
onUrlError(erro)  →  erro.status === 403, erro.code === "ACCOUNT_INACTIVE"

    Prefixo e nome do parâmetro

    Os defaults batem com o make_sse_router do backend: prefix: "/sse" e ticketParam: "ticket". Se o router foi montado em outro lugar, passe os dois. Fora de React, createTicketEventStream({ client: api, ... }) faz o mesmo e devolve o controller com close/reconnect/status.

    Troca de conta na mesma aba — sessionKey

    O ticket abre o canal do usuário que o pediu, e o backend confere o ticket só na abertura: nem o logout nem a revogação do refresh token derrubam um stream já aberto — ele vive até o cliente sair (conferido no make_sse_router e no UserAuthService.sse_router do tempest-fastapi-sdk). Se a aba troca do usuário A para o B sem enabled passar por false, o stream de A continua entregando os eventos de A sob o B.

    Com o api do createTempestAuth: automático

    Desde a 0.82.0, quando o client é o api que o createTempestAuth montou, o stream se amarra sozinho à sessão daquele preset — você não passa sessionKey nem enabled:

    import { createTempestAuth, useTicketEventStream } from "tempest-react-sdk";

interface Usuario {
    id: string;
}

const auth = createTempestAuth<Usuario>({ baseURL: "https://api.exemplo.com" });

export function Avisos() {
    const { status, lastMessage } = useTicketEventStream<{ texto: string }>({
        client: auth.api,
        onMessage: ({ data }) => console.log("aviso", data.texto),
    });

    return (
        <div>
            <span>Stream: {status}</span>
            {lastMessage && <p>{lastMessage.data.texto}</p>}
        </div>
    );
}

    A chave é auth.sessionKey(): a linhagem que o login() cria, mantida em toda rotação de token e limpa no fim da sessão. O que cada evento faz com o stream:

    Evento Stream
    login() de outra conta (ou da mesma) na aba fecha o de antes, zera lastMessage, pede ticket da sessão nova
    login ou logout em outra aba o mesmo, assim que a aba segue o storage
    rotação do token (refresh(), 401 → refresh) nada — mesmo stream, mesma conexão
    logout() ou sessão expirada fecha e fica idle, sem pedir ticket
    ninguém logado ao montar fica idle até o próximo login()

    Medido com o EventSource e o backend mockados em src/sse/session-auth.test.tsx (npx vitest run src/sse/session-auth.test.tsx): na main antes desta mudança, depois de login(B) o stream de A continuava sendo o único EventSource, aberto.

    Quem continua como antes

    Um cliente que o createTempestAuth não montou — createApiClient próprio, um wrapper, uma cópia com spread — não carrega sessão, e o stream segue só url, enabled e o sessionKey que você passar. Um sessionKey explícito sempre ganha do que vem do cliente.

    Com outro cliente: sessionKey

    Passe a identidade da sessão em sessionKey e o hook cuida disso:

    import { createApiClient, useTicketEventStream } from "tempest-react-sdk";

const api = createApiClient({
    baseURL: "https://api.exemplo.com",
    prefix: "/api",
    getToken: () => localStorage.getItem("token"),
});

export function Avisos({ usuario }: { usuario: { id: string } | null }) {
    const { status, lastMessage } = useTicketEventStream<{ texto: string }>({
        client: api,
        enabled: usuario !== null,
        sessionKey: usuario?.id ?? null,
        onMessage: ({ data }) => console.log("aviso", data.texto),
    });

    return (
        <div>
            <span>Stream: {status}</span>
            {lastMessage && <p>{lastMessage.data.texto}</p>}
        </div>
    );
}

    Quando usuario.id muda de "a" para "b":

    EventSource …/sse/stream?ticket=<de a>   fechado
lastMessage                              null
POST …/sse/ticket                        200  {"ticket":"<de b>","expires_in":60}
GET  …/sse/stream?ticket=<de b>          200  text/event-stream
    • A troca de chave fecha o stream, zera lastMessage e pede ticket novo.
    • Um frame de A que chegue entre o render e o efeito que fecha o stream é descartado, não entregue.
    • A chave é um primitivo (string | number | boolean | null | undefined): um objeto montado inline reabriria o stream a cada render.
    • Sem sessionKey, e com um cliente que não veio do createTempestAuth, nada muda: o stream segue só url e enabled.

    Fora de React, createEventStream e createTicketEventStream aceitam sessionKey como função (() => store.getState().user?.id ?? null). A chave é lida a cada conexão e antes de cada frame: frame que chega com a chave trocada é descartado e o stream reconecta para a sessão atual. Como a conferência acontece na chegada de um frame, um stream silencioso só fecha no próximo frame ou no close(). Com client: auth.api e sem sessionKey, o createTicketEventStream segue a sessão do preset na hora da troca, como o hook — e para de seguir no close() (o reconnect() volta a seguir).

    URL resolvida por conexão

    O helper se apoia num recurso do createEventStream/useEventStream que você pode usar direto: url pode ser uma função, chamada antes de cada conexão — a primeira e cada reconexão. Ela pode ser async. Útil para qualquer credencial curta na URL:

    import { createEventStream } from "tempest-react-sdk";

const stream = createEventStream(
    async () => {
        const resposta = await fetch("/api/stream-url", { method: "POST" });
        const { url } = (await resposta.json()) as { url: string };
        return url;
    },
    {
        shouldRetryUrl: (erro) => !(erro instanceof TypeError),
        onUrlError: (erro) => console.error("não deu para montar a URL:", erro),
    },
);

stream.close();

    Cada conexão chama a função de novo — a reconexão inclusive:

    POST /api/stream-url   200  {"url":"https://eventos.exemplo.com/s?sig=A"}
GET  https://eventos.exemplo.com/s?sig=A          (aberto; a rede cai)
POST /api/stream-url   200  {"url":"https://eventos.exemplo.com/s?sig=B"}
GET  https://eventos.exemplo.com/s?sig=B          (aberto)
    • Se a função lança ou rejeita, onUrlError é chamado e o stream re-tenta com backoff — a não ser que shouldRetryUrl devolva false, que leva direto a "error". Essas falhas contam no maxRetries.
    • Uma resolução que termina depois de close() ou reconnect() é descartada.
    • No hook, uma função criada inline não reconecta a cada render: a mais recente é a usada na próxima conexão. Chame reconnect() para aplicar agora. Uma URL string continua reabrindo quando muda.

    Migrando para o tempest-fastapi-sdk >= 0.331.0

    Atualizar o backend troca a rota de stream. Ache a sua linha:

    Como o seu front abre o stream hoje O que acontece depois de atualizar o backend O que fazer
    useEventStream(`${API}/sse/stream?access_token=${token}`) 401 — allow_access_token_query é False por padrão trocar por useTicketEventStream({ client: api })
    useEventStream(url, { withCredentials: true }) com sessão em cookie 401 — o stream não lê cookie trocar por useTicketEventStream com o cliente em withCredentials + csrf (acima)
    createEventStream(url, ...) fora de React o mesmo das linhas acima createTicketEventStream({ client: api, ... })
    endpoint SSE próprio, sem o router pronto do backend nada muda nada — useEventStream continua igual

    As opções (schema, namedEvents, onMessage, enabled, …) são as mesmas; sai só a URL, que o helper monta com o baseURL e o prefix do cliente.

    Migrar sem janela de quebra

    Atualize o backend com sse_router(..., allow_access_token_query=True): ele aceita o ticket e o ?access_token= antigo. Publique o front com o helper, espere os clientes antigos saírem e desligue a opção. Lado do servidor: receita de SSE do tempest-fastapi-sdk (seção "Autenticação").

    Frame que não é JSON

    Por padrão os dois transportes fazem JSON.parse do frame. Quando o parse falha — o servidor devolveu HTML de erro, um ping em texto puro, um proxy injetou algo — o SDK entrega a string crua anunciada como o seu tipo. É o comportamento histórico e ele continua, porque mudá-lo quebraria quem depende dele; o que mudou é que ele parou de ser silencioso.

    import { createEventStream } from "tempest-react-sdk";

interface Evento {
    id: string;
    tipo: string;
}

const socket = createEventStream<Evento>("https://api.exemplo.com/eventos", {
    onParseError: (erro, raw) => {
        console.error("frame ilegível, descartado:", raw.slice(0, 120), erro);
    },
    onMessage: ({ data }) => {
        console.log(data.id);
    },
});

    Com onParseError registrado, o frame quebrado não chega em onMessage — quem pediu para ouvir a falha não pediu para também receber o frame. Sem ele, o frame é entregue como antes e um build de desenvolvimento avisa uma vez por transporte no console.

    Por que o padrão antigo é uma armadilha

    data tipado como Evento sendo na verdade uma string não explode no parse — explode no primeiro data.id, longe dali, sem nada apontando para o frame que causou. O aviso e o onParseError existem para o erro aparecer onde ele acontece.

    parser continua mandando

    Passar parser desliga tudo isso: o resultado dele é entregue, porque decodificar texto, binário em base64 ou um protocolo próprio é justamente o propósito da opção. onParseError só entra em cena quando não há parser. A única coisa que ainda olha o resultado do parser é o schema, quando você passa os dois.

    Validar o frame com schema

    O tipo genérico (createEventStream<Evento>) é uma promessa sobre o servidor que o TypeScript não tem como cumprir: ele apaga em runtime. Um frame sem o campo message chega em onMessage anunciado como Evento, com message: undefined, e o app grava isso no IndexedDB e renderiza uma notificação vazia — sem nenhum erro no caminho.

    Passe schema e validar deixa de ser trabalho do app:

    import { useEventStream } from "tempest-react-sdk";
import { z } from "zod";

const notificacaoSchema = z.object({
    id: z.string(),
    message: z.string(),
});

type Notificacao = z.infer<typeof notificacaoSchema>;

export function Notificacoes() {
    const { status } = useEventStream<Notificacao>("https://api.exemplo.com/notificacoes/stream", {
        namedEvents: ["notification"],
        schema: notificacaoSchema,
        onValidationError: (issues, raw) => {
            console.warn("frame fora do contrato, descartado:", issues, raw.slice(0, 120));
        },
        onMessage: ({ data }) => {
            console.log(data.message);
        },
    });

    return <p>Stream: {status}</p>;
}

    O que a opção garante:

    • sem schema, nada muda — o caminho de hoje continua igual, fallback e aviso inclusive;
    • o frame que não casa não é entregue, a mesma regra que o onParseError já segue, e onValidationError recebe os issues (path pontilhado + message) mais o texto cru;
    • o valor entregue é a saída do schema, então z.coerce, .default() e .transform() valem;
    • parser decodifica primeiro, e o schema valida o que ele devolveu;
    • frame vazio é frame inválido: JSON.parse("") lança, e com schema o texto cru vai para o schema, que o recusa — em vez de chegar como string vazia anunciada como o seu tipo.

    zod, valibot, arktype — e o SDK não depende de nenhum

    O schema aceita qualquer coisa com Standard Schema (~standard, que zod >= 3.24, valibot e arktype implementam) ou com .safeParse — a assinatura que todo usuário de zod já conhece, e que cobre o zod 3.23 anterior ao ~standard. Nenhuma dessas libs entra como dependência: a validação é chamada pela interface.

    A validação tem de ser síncrona

    O frame é decodificado dentro do handler de message e entregue de lá, então não há onde await: um schema assíncrono entregaria os frames na ordem em que as validações resolvessem. Esse caso é reportado em onValidationError, não aguardado. Use z.object(...), não .refine(async ...).

    Declare o schema fora do componente

    O schema é lido quando o stream abre. Um schema construído inline é um objeto novo a cada render — declare no módulo (ou memoize), e o que vale é o que existia na última abertura.

    Sinal que existe em produção, não só em dev

    O aviso único é dev-only (passa por isDevBuild(), que responde certo sozinho em Vite, webpack, Rspack e Parcel — medido) e mora no console de quem estiver com o DevTools aberto. O onValidationError é do app: dispara em qualquer build, e é dele que sai a métrica de "o backend mudou o contrato" — a que chega no seu logger em produção, onde ninguém está olhando console.

    Status

    "idle" | "connecting" | "open" | "closed" | "error":

    • idle — ainda não conectou (ou enabled: false).
    • connecting — handshake em andamento.
    • open — conectado e recebendo.
    • closed — fechado, possivelmente aguardando reconexão.
    • error — esgotou maxRetries, não tenta mais.

    Recap

    • createEventStream(url, options) abre um SSE com reconnect exponencial; o controller expõe close, reconnect e status.
    • url pode ser uma função chamada a cada conexão; useTicketEventStream({ client }) usa isso para pedir um ticket novo em toda reconexão, sem token na URL.
    • useEventStream(url, options) é o wrapper React: amarra o ciclo de vida ao componente, expõe status/lastMessage/reconnect e respeita enabled.
    • sessionKey amarra o stream à sessão: o servidor não derruba stream aberto no logout, então a troca de conta fecha o stream do usuário anterior no cliente. Com client: auth.api, o stream por ticket lê a sessão do próprio cliente — sem sessionKey, e sem reabrir na rotação de token.
    • Heartbeats (default ["ping"]) mantêm o socket vivo sem disparar onMessage.
    • schema valida cada frame antes de entregar: o que não casa não chega em onMessage, e onValidationError diz por quê.
    • Status "error" = esgotou tentativas; ofereça reconnect() ao usuário.
